# ลงสนาม (Longsanam) — แนวคิดของโปรดักต์

> เอกสารนี้เขียนจากระบบที่สร้างจริง ตัวเลขและกลไกทุกอย่างอ้างอิงจากโค้ดในโปรเจกต์
> ไม่ใช่ข้อเสนอบนกระดาษ ส่วนที่ยังไม่ตัดสินใจจะระบุไว้ตรง ๆ ว่ายังเปิดอยู่

---

## หนึ่งประโยค

**ลงสนาม** ทำให้ก๊วนแบดมินตันนัดกันได้จบในลิงก์เดียวในกลุ่ม LINE —
**คนครบ เงินครบ ได้คอร์ต** โดยผู้จัดไม่ต้องออกเงินก่อนและไม่ต้องทวงใคร

คำสัญญานี้วัดได้ด้วยเลขสองตัว: **ผู้จัดควักเงินตัวเองกี่บาท** (เป้าหมายคือศูนย์)
และ **เวลาที่ใช้ไล่ทวงต่อหนึ่งก๊วน**

สิ่งที่ขายไม่ใช่ "หาสนามได้" — Google Maps ทำได้ฟรี และแอปจองสนามที่มีอยู่ในไทย
มีสนามมากกว่าเราหลายเท่า สิ่งที่ขายคือ **ก๊วนเกิดขึ้นจริงและเงินครบ** ซึ่งเป็นคนละ
ปัญหากับการจองสนาม และเป็นช่องที่แอปจองสนามไม่ได้แก้ เพราะ flow ของพวกเขาจบที่
"คนหนึ่งจอง คนนั้นจ่าย"

---

## ทำไมแบดมินตันอย่างเดียว

โปรดักต์นี้เคยตั้งใจรองรับทุกกีฬา ซึ่งเป็นการเลือกที่ผิด — "ทุกกีฬา" แปลว่า
ไม่ได้ออกแบบให้ใครโดยเฉพาะ และทำให้คำสัญญาจางจนไม่มีใครรู้สึกว่าเป็นของตัวเอง

**แบดมินตันคือกีฬาที่โครงสร้างต้นทุนสร้างความเจ็บนี้ขึ้นมาเอง**

- คอร์ตคิดเป็น **รายชั่วโมง** ไม่ว่าจะมาเล่นกี่คน → ต้นทุนคงที่ แต่หัวไม่คงที่
  คนหายสองคน แปลว่าที่เหลือจ่ายแพงขึ้นทันที นี่คือเหตุผลที่การเก็บเงินให้ครบ
  *ก่อน* ถึงมีความหมาย
- มี **ของสิ้นเปลืองรายครั้ง** คือลูกแบด ที่ซื้อเพิ่มระหว่างเล่นและต้องหารกันทีหลัง
  กีฬาอื่นแทบไม่มีค่าใช้จ่ายที่งอกขึ้นกลางเกม
- เล่นกันเป็น **ก๊วนประจำรายสัปดาห์** 6–20 คน ซึ่งใหญ่พอที่การเก็บเงินจะเจ็บ
  และซ้ำพอที่จะกลายเป็นพฤติกรรม

เทียบกับกีฬาอื่น: เทนนิส 2–4 คนหารกันเองได้โดยไม่ต้องใช้เครื่องมือ ·
ฟุตบอลทีมมักเป็นทีมนิ่งที่มีระบบเก็บเงินของตัวเองอยู่แล้ว

**ระบบที่สร้างไว้ก็เป็นแบดอยู่แล้วโดยไม่ได้ตั้งใจ** ซึ่งเป็นหลักฐานว่าการแคบลงนี้
ตรงกับของจริง ไม่ใช่การเลือกบนกระดาษ:

| หลักฐานในโค้ด | ความหมาย |
|---|---|
| `sessions.shuttle_cost_thb` | คอลัมน์ **ค่าลูกแบด** ฝังอยู่ในสคีมาหลัก ไม่มีกีฬาอื่นที่มีของแบบนี้ |
| คำว่า "ก๊วน" ทั้งแอป | เป็นคำที่ใช้กับแบดเป็นหลักในภาษาไทย |
| ตั๋ว LSN-0024 | มีอยู่เพราะค่าลูกแบดและค่าไม้ยืมโดยเฉพาะ |

การแคบลงนี้ **ไม่ต้องแก้ฐานข้อมูล** ตาราง `sports` ยังอยู่เหมือนเดิม
เปลี่ยนเฉพาะการวางตัว หน้าค้นหา และสนามที่ไปคุยด้วย

---

## ปัญหา

การนัดเล่นแบดกับเพื่อนหนึ่งครั้ง ต้องผ่านสองเรื่องที่ขัดกันเอง

**เรื่องที่หนึ่ง — เก็บเงินในกลุ่ม LINE ไม่มีใครอยากทำ**
คนจัดต้องออกเงินค่าสนามไปก่อน แล้วไล่ทวงทีละคน บางคนโอนช้า บางคนลืม
บางคนหายไปเลย คนจัดกลายเป็นเจ้าหนี้ของเพื่อนตัวเอง ซึ่งเป็นบทบาทที่ไม่มีใครสมัครใจรับ
และเป็นเหตุผลที่คนจัดก๊วนหมดไฟ

**เรื่องที่สอง — ไม่มีใครกล้าตัดสินใจก่อน**
- ถ้าจองสนามก่อนแล้วค่อยเก็บเงิน → คนจัดแบกความเสี่ยงคนเดียว ถ้าคนไม่ครบก็จ่ายเอง
- ถ้าเก็บเงินก่อนแล้วค่อยจอง → กว่าจะเก็บครบ สนามอาจเต็มไปแล้ว และต้องคืนเงินทุกคน

นี่คือ **ทางตัน**: จองไม่ได้เพราะยังไม่มีเงิน เก็บเงินไม่ได้เพราะยังไม่แน่ใจว่าจะได้สนาม

---

## Insight

> **เงินกับสนามต้องถูกตัดสินพร้อมกัน ไม่ใช่ตามลำดับ**

ทุกวันนี้คนแก้ปัญหานี้ด้วยความไว้ใจส่วนตัว — คนจัดที่ยอมเสี่ยง หรือกลุ่มที่สนิทกันพอ
จะเรียกเก็บทีหลังได้ ซึ่งแปลว่าก๊วนแบดถูกจำกัดอยู่แค่ในวงที่ไว้ใจกันอยู่แล้ว

ลงสนามไม่ได้แก้ด้วยการทำให้จองสนามง่ายขึ้น (นั่นไม่ใช่ปัญหา)
แต่แก้ด้วยการ **ย้ายความเสี่ยงออกจากตัวคน ไปไว้ที่ระบบ**

เงินของผู้เล่นถูกพักไว้ ไม่ได้เข้ากระเป๋าใคร จนกว่าจะครบเงื่อนไข
พอครบระบบจึงจองสนามให้ ถ้าจองไม่สำเร็จ ทุกคนได้เงินคืนเต็ม
ไม่มีใครต้องเป็นคนตัดสินใจก่อน และไม่มีใครต้องเป็นเจ้าหนี้ของเพื่อน

**มองอีกมุมหนึ่ง โปรดักต์นี้ไม่ใช่แอปจองสนาม แต่เป็น commitment device**
สิ่งที่ขายไม่ใช่ความสะดวก แต่เป็นความแน่นอน

---

## วิธีทำงาน

```
ผู้จัดตั้งก๊วน  →  ส่งลิงก์เข้ากลุ่ม LINE  →  เพื่อนกดเข้าร่วมและจ่าย
                                                      ↓
                                         ครบขั้นต่ำทั้งคนและเงิน
                                                      ↓
                                            คอร์ตถูกยืนยัน
                                              ↓                    ↓
                                     ได้คอร์ต → เจอกัน      ไม่ได้คอร์ต → คืนเงินเต็ม
```

ขั้น "คอร์ตถูกยืนยัน" มีสองทาง และ MVP ใช้ทางแรก:

```
ทาง 1 (MVP)      ผู้จัดกด "ได้คอร์ตแล้ว"  →  booked        ไม่ต้องมีสนามพันธมิตร
ทาง 2 (สร้างแล้ว) ระบบไล่จองตามลำดับที่ผู้จัดอนุมัติ  →  สนามกดยืนยัน  →  booked
```

สถานะของก๊วนมีแปดสถานะ และทุกสถานะบอกผู้ใช้ตรง ๆ ว่ากำลังรออะไรอยู่

| สถานะ | ผู้ใช้เห็นว่า |
|---|---|
| `draft` | ยังไม่เผยแพร่ มีเพียงคุณที่เห็นก๊วนนี้ |
| `open` | กำลังรอผู้เล่นเข้าร่วมและชำระเงินให้ครบขั้นต่ำ |
| `ready_to_book` | ผู้เล่นและยอดเงินครบแล้ว ระบบกำลังจะจองสนามให้ |
| `holding_court` | ระบบกำลังกันคอร์ตและรอสนามยืนยัน |
| `booked` | ยืนยันสนามเรียบร้อย เจอกันในวันนัด |
| `booking_failed` | ลองสนามที่อนุมัติไว้ครบแล้วแต่ยังไม่ได้คอร์ต |
| `cancelled` | ก๊วนนี้ถูกยกเลิก และมีการคืนเงินตามเงื่อนไข |
| `completed` | ก๊วนนี้จบแล้ว |

## กลไกที่เป็นหัวใจ

### 1. ประตูสองบาน — ต้องครบทั้งคนและเงิน

ก๊วนจะจองสนามได้ต่อเมื่อ **ผ่านเกณฑ์สองอย่างพร้อมกัน**: คนจ่ายครบขั้นต่ำ *และ*
เงินที่เก็บได้จริงพอค่าสนาม

เหตุผลที่ต้องนับสองอย่างไม่ใช่อย่างเดียว: ถ้านับแต่จำนวนคน ก๊วนที่มีคนได้ส่วนลด
หรือมีคนขอคืนเงินไปบางส่วน จะไปกระตุ้นการจองที่ผู้จัดจ่ายไม่ไหว

นี่คือจุดที่โปรดักต์ป้องกันไม่ให้ตัวเองสร้างปัญหาเดิมขึ้นมาใหม่

### 2. จ่ายทีหลัง กับเครดิตที่ค้ำมันไว้

ในกลุ่มเพื่อนจริง ๆ มีคนที่ "เดี๋ยวโอนให้" เสมอ ระบบไม่ปฏิเสธความจริงข้อนี้
แต่ทำให้มันมีต้นทุนที่มองเห็นได้

ผู้เล่นทุกคนเริ่มที่เครดิต **100** และ:

| เหตุการณ์ | เครดิต |
|---|---|
| ขอจ่ายทีหลังได้ ต้องมีเครดิตอย่างน้อย | 70 |
| จ่ายภายใน 3 วัน (grace period) | +5 |
| จ่ายช้ากว่านั้นแต่จ่ายครบ | +10 |
| ค้างชำระ วันละ | −5 |
| ไม่มาเล่นและไม่จ่าย | −10 |
| ระบบหยุดทวงที่วันที่ | 14 |

สิ่งที่กลไกนี้ทำจริง ๆ คือ **แปลงความไว้ใจส่วนตัวให้เป็นตัวเลขที่พกติดตัวข้ามก๊วนได้**
เดิมทีคนจัดต้องรู้จักเป็นการส่วนตัวว่าใครเชื่อถือได้ ตอนนี้คนแปลกหน้าก็มีประวัติให้ดู
ซึ่งเป็นสิ่งที่ทำให้ก๊วนขยายออกนอกวงเพื่อนได้

**ข้อสำคัญ**: การให้จ่ายทีหลังจะดึงที่นั่งนั้นออกจากยอดที่ใช้ปลดล็อกการจอง
ผู้จัดต้องเห็นตัวเลขนั้นก่อนกดอนุมัติ ไม่ใช่มารู้ทีหลังตอนก๊วนจองไม่สำเร็จ

### 3. เช็คอิน แล้วหารตามคนที่มาจริง

ค่าสนามที่ผู้จัดกรอกตอนตั้งก๊วนเป็นแค่การเดา พอเล่นจบแล้วระบบให้หารใหม่จาก
**ค่าสนามจริง + ค่าลูกจริง** หารด้วย **คนที่เช็คอินจริง** ไม่ใช่คนที่กดเข้าร่วม

หารได้สองแบบ: หารเท่ากัน หรือหารตามจำนวนเกมที่เล่น
คนที่จ่ายไปแล้วจะไม่ถูกเรียกเก็บเพิ่มย้อนหลัง ส่วนต่างเป็นของผู้จัด

### 4. ผู้เล่นรับเชิญ — และเส้นที่ระบบยอมรับว่าตัวเองทำไม่ได้

เพื่อนที่ไม่มีบัญชีก็ลงชื่อแทนได้ ผู้จัดบอกได้ว่ารับเงินสดมาแล้วหรือยัง

แต่ระบบ **ประกาศข้อจำกัดของตัวเองอย่างชัดเจน**: เงินสดที่ผู้จัดรับไว้เองไม่เคยผ่านระบบ
ถ้าก๊วนถูกยกเลิก ระบบคืนให้ไม่ได้ ผู้จัดต้องคืนเองกับมือ — และหน้าจอยกเลิกก๊วน
จะแยกตัวเลขให้เห็นว่า "ระบบคืนให้เท่านี้" กับ "คุณต้องคืนเองเท่านี้"

การยอมบอกว่าทำอะไรไม่ได้ สำคัญกว่าการแกล้งทำเป็นว่าทำได้ทุกอย่าง

### 5. คืนเงินตามเวลาที่เหลือ

| เงื่อนไข | คืน |
|---|---|
| ระบบจองสนามไม่สำเร็จ | 100% |
| ผู้จัดยกเลิกก๊วน | 100% |
| ยกเลิกเองก่อนเริ่ม ≥ 48 ชม. | 100% |
| ยกเลิกเองก่อนเริ่ม ≥ 24 ชม. | 50% |
| หลังจากนั้น | 0% |

### 6. คิวสำรองอัตโนมัติ

ก๊วนเต็มแล้วยังเข้าคิวได้ พอมีคนสละสิทธิ์ ระบบเลื่อนคิวขึ้นให้เอง
ไม่ต้องมีใครมานั่งดูกลุ่ม LINE ว่าใครถอนตัว

## ทำไมต้อง LINE-first

คนไทยไม่ได้อยากโหลดแอปใหม่เพื่อเล่นแบดอาทิตย์ละครั้ง

การนัดก๊วนเกิดขึ้นในกลุ่ม LINE อยู่แล้ว โปรดักต์จึงไม่พยายามย้ายคนออกมา
แต่เข้าไปอยู่ตรงนั้น — **ลิงก์เดียวที่แชร์เข้ากลุ่มได้ กดแล้วเห็นทุกอย่าง จ่ายได้เลย**
ไม่ต้องสมัคร ไม่ต้องโหลด

ผลที่ตามมาต่อการออกแบบ:

- หน้าเว็บต้องเปิดเร็วบนมือถือกลางแดด → ระบบสีเป็นโหมดสว่างอย่างเดียว โดยตั้งใจ
- ลิงก์คือหน่วยของการเติบโต ทุกก๊วนที่ถูกแชร์คือการแนะนำโปรดักต์ให้คนใหม่ 8–14 คน
- คนที่กดเข้ามาจากลิงก์ต้องเข้าใจได้ทันทีโดยไม่ต้องมีใครอธิบาย

## ผู้ใช้สามกลุ่ม

| กลุ่ม | ได้อะไร | เจ็บตรงไหนถ้าไม่มีโปรดักต์นี้ |
|---|---|---|
| **ผู้จัดก๊วน** | ไม่ต้องออกเงินก่อน ไม่ต้องทวง | เป็นเจ้าหนี้เพื่อน และแบกความเสี่ยงคนเดียว |
| **ผู้เล่น** | รู้แน่ว่าได้เล่นไหม จ่ายแล้วมีหลักประกัน | จ่ายไปแล้วลุ้นว่าจะได้สนามไหม |
| **เจ้าของสนาม** | ได้ลูกค้าเป็นกลุ่มที่จ่ายเงินแล้ว | คอร์ตว่างช่วงนอกพีค และการจองที่ไม่มาจริง |

จุดที่มักถูกมองข้าม: **เจ้าของสนามได้ประโยชน์จากกลไกนี้มากกว่าที่คิด** เพราะก๊วนที่จองผ่าน
ลงสนามคือก๊วนที่เก็บเงินครบแล้ว โอกาสไม่มาจึงต่ำกว่าการจองแบบโทรจอง

**แต่ในช่วง MVP เจ้าของสนามยังไม่ใช่ผู้ใช้** ทางที่ 1 ไม่ต้องให้สนามทำอะไรเลย
สนามเป็นผู้ใช้กลุ่มที่สามเมื่อมีก๊วนจริงมากพอที่จะเอาไปคุยได้ว่า
"เดือนที่แล้วมีก๊วนจองคอร์ตคุณไปกี่ครั้ง" ซึ่งเป็นบทสนทนาที่ง่ายกว่าการขายระบบเปล่า

## เรื่องคอร์ต — คำถามที่ทำให้โปรดักต์นี้ตายได้

ถ้าก๊วนจองคอร์ตไม่ได้ กลไกเงินทั้งหมดก็ไม่มีความหมาย ข้อนี้จึงต้องตอบก่อนข้ออื่น
และต้องตอบตามความจริง ไม่ใช่ตามสิ่งที่อยากให้เป็น

**สถานะวันนี้ อย่างตรงไปตรงมา:** กลไกฝั่งสนามสร้างเสร็จแล้วทั้งหมด — `venues`,
`courts`, `court_availability`, `court_price_rules`, `court_holds`, `bookings`,
`session_venue_preferences` พร้อม Partner Portal ครบทั้ง inbox / calendar /
courts / revenue **แต่สนามพันธมิตรจริงยังเป็นศูนย์แห่ง** และ
`venues.auto_confirm_bookings` มีค่าตั้งต้นเป็น `false` แปลว่าโดยปริยาย
คำขอจองจะไปนั่งรอให้คนที่สนามเปิดแอปมากด

### สามทางที่จะได้คอร์ต

| ทาง | ต้องมีอะไร | สถานะ |
|---|---|---|
| **1. ผู้จัดยืนยันคอร์ตเอง** | ไม่ต้องมีสนามพันธมิตรเลย | **ยังทำไม่ได้** — ดูช่องว่างด้านล่าง |
| 2. Partner Portal | สนามต้องเข้ามาใช้จริง | สร้างเสร็จ รอสนาม |
| 3. เชื่อม API ระบบจองของสนาม | สนามต้องมีระบบก่อน | เว้นที่ไว้ ยังไม่ทำ |

**MVP คือทางที่ 1** เหตุผลไม่ใช่การหลบปัญหา แต่เพราะ **ผู้จัดก๊วนแบดมีคอร์ตประจำ
ของตัวเองอยู่แล้ว** สิ่งที่เขาไม่มีคือกลไกเก็บเงิน เราจึงไม่ควรไปแก้ปัญหาที่เขาไม่ได้มี
และไม่ควรผูกชะตาของโปรดักต์ไว้กับการต้องชนะฝั่งสนามให้ได้ก่อน

### ช่องว่างที่ต้องปิดก่อน และมันเล็กกว่าที่คิด

ตรวจโค้ดแล้ว มีเพียง **สองทาง**ที่ทำให้ก๊วนกลายเป็น `booked` ได้:
`request_booking()` เมื่อสนามเปิด auto-confirm และ `venue_decide_booking()`
ซึ่งกั้นด้วย `is_venue_member()` — **ผู้จัดจึงกดยืนยันคอร์ตเองไม่ได้ในวันนี้**

แต่ครึ่งหลังมีอยู่แล้ว: `settle_session_costs()` รองรับกรณี "สนามยืนยันทางโทรศัพท์
และไม่มีอะไรถูกจองในแอป" ไว้เรียบร้อย โดยใช้ราคาคอร์ตที่ถูกที่สุดที่ผู้จัดอนุมัติไว้
เป็นฐานคิดเงิน

สิ่งที่ขาดคือ RPC ตัวเดียวให้ผู้จัดกด "ได้คอร์ตแล้ว" แล้วบันทึกการจองแบบกรอกเอง
พร้อมย้ายสถานะไป `booked` — **หนึ่งตั๋ว ไม่ใช่หนึ่งเฟส**

### ข้อนี้ตอบด้วยโค้ดไม่ได้ ต้องตอบด้วยหลักฐาน

แผนพิสูจน์: เลือก **หนึ่งย่าน** ไล่รายชื่อสนามแบดในย่านนั้น ติดต่อจริง
แล้วรายงานว่ากี่แห่งตกลง เกณฑ์ผ่านคือ **สนาม 2–3 แห่ง กับก๊วนจริง 2 ก๊วน
ที่เล่นซ้ำได้ 4 สัปดาห์** ตัวเลขนั้นคือคำตอบของคำถามนี้ ไดอะแกรมไม่ใช่

## ขอบเขต MVP

**ทำ**: แบดมินตันอย่างเดียว · หนึ่งย่าน · ผู้จัดยืนยันคอร์ตเอง ·
กลไกเก็บเงินและหารเงินเต็มรูปแบบ

**ยังไม่ทำ โดยตั้งใจ**:
- กีฬาอื่น
- เชื่อม API ระบบจองของสนามโดยตรง — สถาปัตยกรรมเว้นที่ไว้แล้ว
  เพราะสนามส่วนใหญ่ในไทยยังใช้สมุดจดหรือ LINE
- ขยายหลายจังหวัด
- แอปเนทีฟ

**เหตุผลของการเว้นไว้**: ปัญหาที่โปรดักต์นี้แก้คือปัญหาระหว่างคนกับคน ไม่ใช่ปัญหาทางเทคนิค
การไปเชื่อม API ก่อนพิสูจน์ว่ากลไกเงินใช้ได้จริง คือการแก้ปัญหาที่ยังไม่ใช่คอขวด

## ตัวชี้วัดที่ควรวัด

**ตัวชี้วัดหลัก** — สัดส่วนก๊วนที่ถึงสถานะ `booked` จากทั้งหมดที่ถูกสร้าง
เพราะมันวัดสิ่งเดียวกับที่โปรดักต์สัญญาไว้ คือ "ตั้งก๊วนแล้วได้เล่นจริง"

**ตัวชี้วัดรอง**
- เวลาเฉลี่ยจาก `open` ถึง `ready_to_book` (ความเร็วในการเก็บเงินครบ)
- อัตราการกลับมาตั้งก๊วนซ้ำของผู้จัดคนเดิม — ตัวชี้วัดที่แท้จริงว่าความเจ็บหายไปไหม
- สัดส่วนผู้เล่นใหม่ที่มาจากลิงก์ที่แชร์ในกลุ่ม (viral coefficient)
- อัตราการค้างชำระของกลุ่มที่ใช้ "จ่ายทีหลัง" เทียบกับที่ไม่ใช้

**ตัวชี้วัดที่ไม่ควรหลงวัด**: จำนวนผู้สมัครสมาชิก โปรดักต์นี้ตั้งใจให้คนใช้ได้โดยไม่ต้องสมัคร

## ความเสี่ยง

| ความเสี่ยง | ทำไมถึงน่ากลัว |
|---|---|
| **ปัญหาไก่กับไข่** | ไม่มีสนามพันธมิตร → ก๊วนจองไม่ได้ · ไม่มีก๊วน → สนามไม่อยากเข้าร่วม · **ลดความเสี่ยงแล้ว** ด้วยการให้ MVP เดินได้โดยไม่ต้องมีสนามพันธมิตร (ดูหัวข้อ "เรื่องคอร์ต") แต่ยังไม่หายไป |
| **การถือเงินของคนอื่น** | มีนัยทางกฎหมายและภาษี ต้องออกแบบร่วมกับผู้ให้บริการชำระเงิน |
| **ก๊วนที่สนิทกันอยู่แล้วไม่ต้องการสิ่งนี้** | กลุ่มที่ไว้ใจกันดีอยู่แล้วไม่มีปัญหาที่ต้องแก้ ตลาดจริงคือกลุ่มที่กำลังโต |
| **สนามไม่กดยืนยันในเวลา** | Partner Portal พึ่งพาคน ถ้าเจ้าของสนามไม่เปิดดู ก๊วนจะค้าง — เป็นเหตุผลที่ MVP ไม่พึ่งทางนี้ |
| **ผู้จัดโกหกว่าได้คอร์ตแล้ว** | ทางที่ 1 เชื่อคำของผู้จัด ถ้าเขากดยืนยันทั้งที่ยังไม่ได้คอร์ต ผู้เล่นจ่ายไปแล้วแต่ไม่ได้เล่น · บรรเทาด้วยนโยบายคืนเงินที่มีอยู่แล้วและเครดิตของผู้จัด แต่ต้องเฝ้าดูจริง |

## รายได้มาจากไหน

> ตัวเลขในหัวข้อนี้เป็น **ประมาณการจากราคาตลาด** ไม่ได้มาจากข้อมูลการใช้งานจริง
> ของเรา ต่างจากส่วนอื่นของเอกสารนี้ที่อ้างอิงโค้ด จึงระบุไว้ให้ชัด

### หน่วยเศรษฐกิจของก๊วนแบดหนึ่งครั้ง

คอร์ตในกรุงเทพประมาณ ฿150–250 ต่อชั่วโมง ก๊วน 8 คนเล่น 2 ชั่วโมง 2 คอร์ต
≈ **฿600–1,000 ต่อครั้ง** หรือ **฿75–125 ต่อหัว** และก๊วนประจำเล่นซ้ำทุกสัปดาห์
≈ 4 ครั้งต่อเดือน

### สามโมเดลที่เป็นไปได้

| โมเดล | รายได้ต่อก๊วนต่อครั้ง | ติดตรงไหน |
|---|---|---|
| หัก % จากค่าสนาม 5–10% | ฿40–80 | **ต้องเป็นช่องทางจองก่อน** = ผูกกับปัญหาไก่กับไข่พอดี |
| ค่าธรรมเนียมต่อหัว ฿5–10 | ฿40–80 | ได้เงินโดยไม่ต้องมีสนาม แต่ผู้เล่นรู้สึกทุกครั้ง และดันเราไปเป็นผู้ให้บริการชำระเงิน |
| **ผู้จัดจ่ายรายเดือน ฿99–199 ต่อก๊วน** | ฿25–50 | ผู้เล่นไม่รู้สึกอะไรเลย · รายได้คาดการณ์ได้ · ไม่ต้องรอสนาม |

### ข้อเสนอ: เก็บจากผู้จัดเป็นรายเดือน

**เหตุผลที่หนึ่ง — เก็บเงินจากคนที่เจ็บ** ผู้จัดคือคนที่ออกเงินก่อนและไล่ทวง
คนหายสองคนครั้งเดียวทำให้เขาขาดทุนมากกว่าค่าสมาชิกทั้งเดือน ความเต็มใจจ่าย
จึงอยู่ที่เขา ไม่ใช่ที่ผู้เล่น

**เหตุผลที่สอง — เป็นโมเดลเดียวที่ไม่ต้องชนะฝั่งสนามก่อน** ซึ่งทำให้มันเข้ากันได้กับ
MVP ในหัวข้อ "เรื่องคอร์ต" ที่ตั้งใจไม่พึ่งสนามพันธมิตร

**เหตุผลที่สาม และเป็นข้อที่มักถูกมองข้าม — มันเปลี่ยนสถานะทางกฎหมายของเรา**
ความเสี่ยงเรื่อง "การถือเงินของคนอื่น" ในตารางด้านบนจะหนักขึ้นมากถ้าเราหักส่วนแบ่ง
จากเงินที่ไหลผ่าน เพราะนั่นทำให้เราดูเหมือนผู้ให้บริการชำระเงิน ส่วนการเก็บค่าสมาชิก
รายเดือนทำให้เรายังเป็น **บริษัทซอฟต์แวร์** ที่บังเอิญมีการชำระเงินอยู่ข้างใน

**เก็บไว้เป็นทางสำรอง:** ค่าธรรมเนียมต่อหัวสำหรับก๊วนขาจรที่ไม่เล่นประจำ
ซึ่งไม่คุ้มที่จะสมัครรายเดือน

**ยังไม่ทำในช่วงพิสูจน์ตลาด:** ฟรีทั้งหมด จนกว่าจะมีก๊วนที่เล่นซ้ำได้ 4 สัปดาห์
เพราะการเก็บเงินก่อนที่โปรดักต์จะพิสูจน์ตัวเองคือการวัดผลที่ผิด

## สรุปสำหรับหน้าเดียว

> ก๊วนแบดในไทยนัดกันในกลุ่ม LINE อยู่แล้ว แต่ติดอยู่ที่สองอย่าง —
> ไม่มีใครอยากเป็นคนออกเงินก่อนแล้วไล่ทวง และไม่มีใครกล้ายืนยันคอร์ตก่อนรู้ว่าคนครบ
>
> ลงสนามแก้ด้วยการทำให้ **เงินกับคอร์ตถูกตัดสินพร้อมกัน** — ผู้เล่นจ่ายผ่านลิงก์เดียว
> เงินถูกพักไว้ ไม่เข้ากระเป๋าใคร พอครบทั้งคนและเงิน คอร์ตจึงถูกยืนยัน
> ถ้าไม่ได้คอร์ต คืนเต็มทุกคน
>
> เราไม่ได้ขาย "หาสนามได้" — เราขาย **ก๊วนเกิดจริงและเงินครบ**
> วัดที่ผู้จัดควักเงินตัวเองเท่าไร เป้าหมายคือศูนย์
>
> รายได้มาจากผู้จัดที่จ่ายรายเดือน เพราะเขาคือคนที่เจ็บ และเป็นโมเดลเดียว
> ที่ไม่ต้องรอให้ชนะฝั่งสนามก่อน
