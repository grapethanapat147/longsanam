ตราหลัก viewBox 120 × 120, stroke 18, หัวรัศมี 11 หน่วย; เว้น clear space อย่างน้อย 22 หน่วยรอบกรอบตราเมื่อจัดวาง ไม่รวมอยู่ใน viewBox

ตราหลักใช้ได้ตั้งแต่ 16px; lockup พร้อม descriptor ควรกว้างอย่างน้อย 240px ในเว็บ ห้ามย่อจน descriptor อ่านไม่ออก ให้ใช้ compact แทน สี reverse ใช้บนพื้น brand-700 หรือเข้มกว่า

รูปคนเป็น stroke path ที่ปรับความหนาได้ ชื่อแบรนด์ยังเป็น text พร้อม embedded font เพื่อแก้คำได้ บางโปรแกรมนำเข้า SVG อาจไม่อ่าน embedded font จึงแนบไฟล์ฟอนต์มาให้ติดตั้งก่อน หากส่งโรงพิมพ์ให้ตรวจฟอนต์และแปลงข้อความเป็น outline ในเครื่องมือออกแบบก่อนส่ง

## Design System — Court Flow

คงสีทุกค่าจากระบบเดิม, Light only, Bai Jamjuree 700 + Anuphan 400/600, Thai line-height ≥1.7 และ letter-spacing 0

- `system/tokens.json` — สีพร้อมบทบาท, spacing, typography, radius, motion, semantic และข้อเสนอการแสดงคะแนน
- `system/tokens.css` — CSS variables ของสีและพื้นฐาน
- `system/components.css` — สไตล์คอมโพเนนต์ตัวอย่างของคู่มือ ต้องจำกัด scope ก่อนนำไปผสมกับ CSS แอปจริง
- `system/components.json` — สเปกตัวเลขที่ใช้ส่งต่อ
- `system/contrast.json` — ผลคำนวณคู่สีที่ใช้กับข้อความ/องค์ประกอบสำคัญ
- `system/browser-checks.json` — ผลตรวจ responsive และ interaction

ตัวอย่างประกอบด้วย tournament card, squad/individual skill, court cost summary, ปุ่มหลายสถานะ, native date/time picker พร้อมวันที่ไทย, bottom sheet, rule review, check-in, friend request, rating, empty, skeleton, error, toast และ flow นัดครั้งหน้า

ขอบการ์ด ink-200 ใช้แบ่งพื้นที่ ไม่ใช้แทนขอบปุ่มหรือ input ซึ่งต้องใช้ ink-400 ส่วนไลม์เป็นพื้น/กราฟิก ไม่ใช้เป็นข้อความ ปุ่ม brand-500 ใช้ข้อความ ink-900

## Product assumptions สำหรับ prototype นี้

ข้อเหล่านี้เป็นข้อเสนอออกแบบ ไม่ใช่กติกาที่ได้รับการยืนยันหรือระบบที่พัฒนาเสร็จแล้ว

1. 1 ก๊วน = 1 ทีมในระดับกิจกรรม ขั้นต่ำ 2 ก๊วน ค่าเริ่มต้น 4 ก๊วน = เจ้าภาพ 1 + ผู้ร่วม 3 ก๊วน ภายในก๊วนต้องระบุ roster และคู่แข่งขันต่อแมตช์
2. ผู้จัดเลือกวัน เวลา สนาม 2 คอร์ต และระดับที่อยากเจอ สนามยืนยันแล้วจึงเปิดรับก๊วนได้ การยืนยันสนามใน prototype เป็น checkbox จำลอง
3. จำนวนก๊วนกับสถานะจองสนามแยกจากกัน ก่อนเริ่มแข่งต้องอย่างน้อย 2 ก๊วน เช็กอินและทวนกติกาแล้ว การแข่งเมื่อยังไม่ถึงจำนวนเป้าหมายจริงต้องให้ผู้จัดตกลงรูปแบบและค่าใช้จ่ายใหม่
4. แสดงหัวข้อกติกาที่ผู้จัดต้องกำหนดก่อนงาน ไม่อ้างว่าเป็นกติกาการแข่งขันทางการ การสร้าง bracket, การจัดเวลาแต่ละแมตช์, รายชื่อผู้เล่น และการบันทึกคะแนนเกมจริงเป็นขั้นพัฒนาต่อ
5. หลังแมตช์ ทั้งสองฝั่งต้องยืนยันผลตรงกันก่อนประเมิน กรณีขัดแย้งให้รอผู้จัดตรวจ ยังไม่ส่งผลต่อคะแนน
6. Friend request ต้องรออีกฝ่ายตอบรับ ไม่เพิ่มเป็นเพื่อนทันที ไม่ส่งข้อความออกไปภายนอก
7. ตัวอย่างค่าใช้จ่าย 2 คอร์ต × ฿300/ชั่วโมง × 2 ชั่วโมง = ฿1,200 หรือ ฿300/ก๊วนเมื่อครบ 4 ก๊วน ข้อเสนอนี้ยังไม่กำหนด payment, refund หรือค่าธรรมเนียมของธุรกิจ

## วิธีแสดงระดับฝีมือที่เสนอ

- ระดับที่ผู้เล่นระบุเอง: มือใหม่ / เริ่มคล่อง / ชอบแข่งขัน เป็นข้อมูลเริ่มต้น ไม่ทำให้ดูเหมือนผ่านการวัดแล้ว
- คะแนนฝีมือรายคน: ค่าเฉลี่ย 1–5 จากคู่แข่งหลังแมตช์ที่ยืนยันผล พร้อมจำนวนการประเมิน คนหนึ่งประเมินคู่แข่งคนเดิมได้ 1 ครั้งต่อแมตช์ ไม่ให้ประเมินตนเองหรือเพื่อนก๊วนเดียวกัน
- เสนอให้ติด “ข้อมูลยังน้อย” ถ้ามีการประเมินจากน้อยกว่า 3 แมตช์ ไม่แสดงผู้ไม่มีคะแนนเป็น 0
- คะแนนก๊วน: ค่าเฉลี่ยคะแนนรายคนใน roster ที่ยืนยันสำหรับงานนั้น แสดง `มีคะแนนกี่คน / ผู้เล่นทั้งหมด` ชัดเจน ถ้าไม่ครบทุกคนยังไม่ใช้คัดระดับอัตโนมัติ
- ตัวอย่าง 4 คน: (3.4 + 3.0 + 3.2 + 3.2) / 4 = 3.2; แต่ละคนมี 5 การประเมิน รวม 20 การประเมิน ไม่เท่ากับ 20 ผู้ประเมินที่ไม่ซ้ำกัน
- แยกน้ำใจนักกีฬา 1–5 ออกจากฝีมือ และแยกจำนวนแมตช์จริงออกจากจำนวนความคิดเห็น
- ไม่ผูกคะแนน 1–5 กับระดับมือใหม่/เริ่มคล่องอย่างตายตัวใน MVP ก่อนทดสอบกับผู้เล่นจริง ความลำเอียงของกลุ่มคู่แข่งอาจทำให้คะแนนต่างกลุ่มเปรียบเทียบกันไม่ได้
- ระบบต่อไปควรมีประวัติผู้ประเมินที่ตรวจสอบได้โดยระบบ การรายงานการประเมินไม่เหมาะสม และการทบทวนข้อโต้แย้ง โดยไม่เปิดให้คะแนนกลายเป็นพื้นที่โจมตีกัน

## สิ่งที่เปลี่ยนจาก brief เก่าอย่างตั้งใจ

ใช้คำขอล่าสุดเป็นหลัก: จาก booking ก๊วนทั่วไปเป็น Social Tournament Club ที่เริ่มจากแบดมินตัน และใช้ A / Flow Runner ตามที่เลือก จึงไม่คงหุ่นมีใบหน้า กระดูกตายตัว เงาใต้เท้า หรือเงื่อนไขซ่อนตัว “ล” จาก brief รุ่นเก่า ไม่สร้างมาสคอตอีก 4 กีฬาในชุดนี้ เพราะโจทย์ใหม่นี้เน้นไม้แบดและวงจร tournament

สี ฟอนต์ และหลักอ่านง่ายยังคงไว้ คู่มือชุดนี้อยู่แยกจากเวอร์ชันก่อนและไม่ได้แก้ไฟล์แอปจริงที่ brief อ้างถึง

## การสร้างไฟล์ใหม่และขอบเขต

ใช้ Python standard library รัน `source/build.py` จากโฟลเดอร์ใดก็ได้ ไฟล์ source, fonts และ system/tokens.json ต้องอยู่ครบ ภาพ screenshot ไม่ถูกสร้างโดย script นี้

ทดสอบเปิดใน Chrome ที่ความกว้าง 320, 390, 768, 1440px; ตรวจเวลาไม่ถูกต้อง, booking gate, ขั้นต่ำ 2 ก๊วน, เต็ม 4 ก๊วน, check-in/rules, friend/rating, rematch, Escape/focus return และ reduced motion ผ่านตามผลแนบ การทดสอบนี้ไม่ใช่ accessibility audit เต็มรูปแบบ

ไม่มี backend, การจองจริง, ตัดเงิน, บันทึกคะแนนถาวร หรือการ publish จริง ข้อมูลในหน้าเป็นข้อมูลสมมุติ คะแนนหลังทดลองกรอกไม่ถูกนำไปรวมกับคะแนนตัวอย่างเก่า การเปิดหน้าใหม่จะล้างการทดลอง

ฟอนต์และ license OFL อยู่ใน `fonts/`.
