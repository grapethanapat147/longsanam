# Badge — เหรียญหลังจบทัวร์นาเมนต์

**สถานะ:** spec · artwork เสร็จแล้ว · ยังไม่มีโค้ด
**เกี่ยวข้อง:** `.codex/specs/tournaments.md` · `docs/design/social-tournament/badges/`

---

## ทำไมต้องมี

ทัวร์นาเมนต์จบแล้วไม่เหลืออะไรเลยนอกจากความทรงจำ badge คือสิ่งที่ทำให้
**การลงแข่งครั้งนี้มีผลกับครั้งหน้า** ซึ่งเป็นกลไกที่ Strava พิสูจน์มาแล้วว่าทำให้คนกลับมา

แต่ badge มีสองด้าน — ถ้าได้ง่ายเกินไปมันไม่มีค่า และถ้าปั่นได้มันกลายเป็น
**ช่องโกงแบบเดียวกับที่ `tournaments.md` ตัดสินไปแล้วว่าจะไม่เปิด** ตอนห้ามไม่ให้
คะแนนกำหนดรุ่นมาจากการประเมินกันเอง เหตุผลเดียวกันใช้ที่นี่: อะไรที่มีมูลค่าจะถูกปั่น

## สิ่งที่มีแล้ว

`docs/design/social-tournament/badges/` — artwork หกใบ native vector
พร้อม `badge-definitions.json` ที่เสนอชื่อและกติกาการให้ไว้แล้ว

| id | ชื่อ | ระดับ | ให้เมื่อ (ข้อเสนอ) |
|---|---|---|---|
| `01-first-tournament` | ทัวร์นาเมนต์แรก | rare | ทัวร์นาเมนต์แรกเป็น completed และอยู่ในรายชื่อที่เข้าร่วมจริง |
| `02-new-opponents` | คู่แข่งใหม่ | common | จบแมตช์ที่ยืนยันผลแล้วกับก๊วนใหม่ครั้งแรก |
| `03-five-tournaments` | ขยับอีกขั้น | rare | แข่งจบ 5 รายการที่ไม่ซ้ำกัน |
| `04-champion` | แชมป์ประจำรายการ | elite | ผู้จัดยืนยันอันดับหนึ่ง |
| `05-fair-play` | น้ำใจนักกีฬา | common | ได้รับคำชื่นชมจากคู่แข่งหลังแมตช์ที่ยืนยันผล |
| `06-three-squads` | เพื่อนร่วมสนาม | rare | แข่งกับก๊วนต่างกันครบ 3 ก๊วน |

## สิ่งที่ยังไม่มี — และ badge พึ่งมันทั้งหมด

ตรวจกับฐานข้อมูลจริงแล้ว **ไม่มีตารางไหนเลย**: `tournaments`, `teams`,
`matches`, ผลแมตช์ที่ยืนยัน, และก๊วนที่คงอยู่ข้ามครั้ง

ทั้งหกใบอ้างถึง "ทัวร์นาเมนต์" หรือ "แมตช์ที่ยืนยันผล" จึง **ให้ใครไม่ได้เลย
สักใบในวันนี้** ตั๋วนี้จึงถูกบล็อกจนกว่า LSN-0027 → LSN-0026 → ทัวร์นาเมนต์จะเสร็จ

## Design

### catalog ไม่ต้องมีตารางในฐานข้อมูล

badge ไม่ได้เพิ่มบ่อย และตาราง catalog แปลว่าต้อง seed ให้ตรงกันทุก environment
แล้วก็จะมีวันที่ staging มีหกใบ prod มีห้าใบ

เก็บเป็น **ค่าคงที่ฝั่ง TypeScript** ที่อ่านจาก `badge-definitions.json` ตรง ๆ
หลักการเดียวกับที่ LSN-0024 ตัดสินว่าชิปกดเติมชื่อรายการไม่ต้องมีตารางใหม่

### ตารางเดียวที่ต้องมี

```sql
create table public.player_badges (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references public.profiles(id) on delete cascade,
  badge_id     text not null,
  awarded_at   timestamptz not null default now(),
  tournament_id uuid references public.tournaments(id) on delete set null,
  unique (user_id, badge_id)
);
```

`unique (user_id, badge_id)` ไม่ใช่แค่กันข้อมูลซ้ำ มันคือสิ่งที่ทำให้ฟังก์ชัน
ให้ badge **เรียกซ้ำได้โดยไม่พัง** ซึ่งจำเป็น เพราะเราจะเรียกมันทุกครั้งที่แมตช์จบ
โดยไม่ต้องจำว่าเคยเรียกไปแล้วหรือยัง

### ให้ตอนไหน

ฟังก์ชันเดียว `award_badges(p_user_id uuid, p_tournament_id uuid)` ที่
**ประเมินทุกใบทุกครั้ง** แล้ว insert อันที่ยังไม่มี — ไม่ใช่ฟังก์ชันละใบ

เรียกจากจุดที่สถานะเปลี่ยนจริง: ทัวร์นาเมนต์กลายเป็น `completed`
และแมตช์ถูกยืนยันผลจากทั้งสองฝั่ง

`on conflict (user_id, badge_id) do nothing` — ไม่ใช่ `do update`
วันที่ได้ครั้งแรกคือวันที่ควรอยู่ในประวัติ ไม่ใช่วันที่ระบบเผลอเรียกซ้ำ

### แสดงที่ไหน

- หน้าโปรไฟล์ — ตารางสะสม ใบที่ยังไม่ได้แสดงเป็นเงาจาง
- การ์ดแชร์หลังจบงาน — ใบที่เพิ่งได้

ใช้ `badges/icons/` (~600–1,000 ไบต์ต่อใบ) **ไม่ใช่** `badges/labeled/`
ซึ่งฝังฟอนต์ทั้งตัวจนใบละ 419KB รวมหกใบ 2.4MB — แพงเกินไปสำหรับแอปที่เปิดจาก LINE
บนเน็ตมือถือ แอปมีฟอนต์อยู่แล้วที่ `src/assets/fonts/` จึงวางคำเองได้

ในตารางสะสมใช้ **64px ไม่ใช่ 48px** — จาก `badge-48px-check.png` ใบ
`02-new-opponents` กับ `05-fair-play` มีรายละเอียดมากกว่าเพื่อนและจมที่ 48px

## กติกาที่กันการปั่น

**นี่คือส่วนที่สำคัญที่สุดของ spec นี้ ไม่ใช่ส่วนภาพ**

1. **badge ห้ามไปขยับ `player_credit` และห้ามไปขยับคะแนนฝีมือ ไม่ว่าทางใด**
   สามอย่างนี้วัดคนละเรื่องและต้องแยกขาดจากกัน เหตุผลเดียวกับที่
   `tournaments.md` แยกเครดิตออกจากคะแนนฝีมือไว้แล้ว
2. **`05-fair-play` ต้องมีผู้ชื่นชมอย่างน้อยหนึ่งคนที่ไม่ได้อยู่ก๊วนเดียวกัน**
   และไม่ประเมินตนเอง — ถ้าเพื่อนในก๊วนกดให้กันได้ มันคือ badge ที่ทุกคนมี
   ภายในสัปดาห์เดียว แล้วก็ไม่มีความหมายอีกเลย
3. **badge ที่ได้จากการนับ (`03`, `06`) ต้องนับจากแมตช์ที่ยืนยันผลแล้วเท่านั้น**
   ไม่ใช่จากการสมัคร ไม่งั้นสมัครแล้วไม่ไปก็ได้ badge

## Non-goals

- ไม่มี badge ที่ซื้อได้ ไม่มี badge ที่ผู้จัดแจกเองตามใจ
- ไม่มี leaderboard เรียงจำนวน badge — นั่นเปลี่ยนโปรดักต์เป็นเกมสะสม
- ไม่มี badge ที่ให้จากคะแนนประเมินฝีมือ
- ไม่ทำ badge เฉพาะกิจรายอีเวนต์ในรอบแรก

## Open Questions — ยังไม่ตัดสิน

### 1. `04-champion` ต้องมีกี่ก๊วนถึงจะนับเป็นแชมป์

`tournaments.md` ตัดสินว่าขั้นต่ำคือ **2 ทีม** ซึ่งแปลว่าชนะคู่แข่งก๊วนเดียว
ก็ได้ badge ระดับ **elite** ซึ่งเป็นระดับที่หายากที่สุดในทั้งชุด

ถ้าปล่อยแบบนี้ คนจะจัดงานสองก๊วนกับเพื่อนแล้วผลัดกันเป็นแชมป์ และ badge
ระดับ elite จะเฟ้อภายในเดือนเดียว **เสนอ: ต้องมีอย่างน้อย 4 ก๊วน**
แต่ยังไม่ตัดสิน เพราะมันขัดกับขั้นต่ำที่ตัดสินไปแล้วและต้องดูของจริงก่อน

### 2. ถอน badge คืนได้ไหมถ้าผลแมตช์ถูกแก้ทีหลัง

`tournaments.md` บอกว่ากรณีผลขัดแย้งให้ผู้จัดตรวจ ซึ่งแปลว่าผลเปลี่ยนได้
ถ้าเปลี่ยนแล้วแชมป์เปลี่ยน badge ที่ให้ไปแล้วควรหายไหม

การถอนของที่ให้ไปแล้วเป็นประสบการณ์ที่แย่มาก แต่การปล่อยให้แชมป์มีสองคน
ก็ทำให้ทั้งระบบไม่น่าเชื่อถือ

### 3. คนนอกก๊วนเห็น badge ของคนอื่นไหม

ใบเสร็จวันนี้ **ปิดรายชื่อผู้เล่นจากคนนอกก๊วน** (LSN-0023) ถ้าโปรไฟล์เปิด badge
ให้ทุกคนเห็น มันจะขัดกับหลักนั้น แต่ badge ที่ไม่มีใครเห็นก็เสียเหตุผลของการมีอยู่ไปครึ่งหนึ่ง
