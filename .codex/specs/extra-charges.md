# รายการเก็บเงินเพิ่ม — extra charges after the whistle

## Problem

ก๊วนจบแล้วเงินยังไม่จบ ค่าลูกแบดที่ซื้อเพิ่มระหว่างเล่น ค่าไม้ที่สองคนยืมจากสนาม
ค่าน้ำที่ผู้จัดออกไปก่อน — ทุกอย่างนี้เกิด *หลัง* ตอนที่ทุกคนจ่ายค่าหัวไปแล้ว

ทุกวันนี้ผู้จัดพิมพ์ลงกลุ่ม LINE ว่า "ค่าลูกเพิ่มคนละ 30 โอนมาด้วยนะ" แล้วก็ไล่ทวงเอง
ซึ่งคือสิ่งเดียวกับที่โปรดักต์นี้ตั้งใจจะกำจัดออกไปตั้งแต่แรก

LSN-0021 แก้ปัญหานี้ไปครึ่งหนึ่งแล้ว: มันหารค่าสนามกับค่าลูกตามคนที่มาจริง
แต่มันเก็บค่าลูกไว้ใน **ช่องเดียว** ชื่อ `sessions.shuttle_cost_thb` ซึ่งแปลว่า

- ใส่ได้ค่าเดียว ตั้งชื่อไม่ได้ แยกไม่ได้ว่าเป็นค่าอะไร
- หารเท่ากันทุกคนเสมอ — ทั้งที่ค่าไม้ควรลงเฉพาะคนที่ยืม
- ผู้จัดต้องรู้ยอดทั้งหมดตอนกดสรุปครั้งเดียว ถ้านึกออกทีหลังต้องกดสรุปใหม่

## Goal

ผู้จัดสร้าง **รายการค่าใช้จ่ายหลายบรรทัด** ต่อหนึ่งก๊วนได้ แต่ละบรรทัดเลือกได้ว่า
หารทั้งก๊วนหรือลงเฉพาะคนที่ระบุ แล้วระบบเรียกเก็บให้ โดยไม่ต้องไล่ทวงในกลุ่ม

## Non-goals

- ไม่ทำระบบสต็อกอุปกรณ์ ไม่ผูกกับสินค้าของสนาม — เป็นแค่ชื่อกับจำนวนเงินที่ผู้จัดพิมพ์เอง
- ไม่ให้ผู้เล่นสร้างรายการเอง ผู้จัดคนเดียวเท่านั้น
- ไม่ทำการคืนเงินรายการเพิ่มเติม ถ้าผู้จัดพิมพ์ผิดให้ลบทั้งบรรทัดแล้วสร้างใหม่
- ไม่แตะ `budget_per_person_thb` ซึ่งเป็นยอดที่ผู้เล่นตกลงตอนกดเข้าร่วม

## ข้อเสนอสำหรับคำถามที่เปิดอยู่ห้าข้อ

เกรพถามไว้ห้าข้อ นี่คือข้อเสนอของผมพร้อมเหตุผล — **ทั้งห้าข้อยังแก้ได้** ก่อนเริ่มเขียนโค้ด

### 1. หารทั้งก๊วน หรือลงเฉพาะบางคน?

**เสนอ: ได้ทั้งสองแบบ เลือกต่อบรรทัด**

แต่ละบรรทัดมี `split_mode` ของตัวเอง:

| โหมด | ใช้กับอะไร | ใครโดน |
| --- | --- | --- |
| `all` | ค่าลูกแบด ค่าน้ำ ค่าสนามเพิ่มชั่วโมง | ทุกคนที่นับในตัวหาร (ใช้กติกาเดียวกับ LSN-0021 คือคนที่เช็คอิน ถ้าไม่มีใครเช็คอินเลยก็ทุกคนที่ถือที่นั่ง) |
| `named` | ค่าไม้ ค่ารองเท้า ของที่ยืมเฉพาะคน | เฉพาะ participant ที่ผู้จัดเลือก |

นี่เป็นเหตุผลหลักที่ฟีเจอร์นี้ไม่ควรเป็นแค่การเพิ่มช่องใน `settle_session_costs`
เพราะ `split_mode` เดิม (`equal` / `by_games`) เป็นของทั้งก๊วน ไม่ใช่ของรายบรรทัด

### 2. สร้างได้ตอนไหน?

**เสนอ: เฉพาะก๊วนที่เกิดขึ้นจริงแล้ว — `booked` หรือ `completed`**

ใช้ **allowlist ไม่ใช่ denylist** ด้วยเหตุผลเดียวกับที่ `mark_no_shows` ต้องใช้:
ถ้าเขียนเป็น "ยกเว้น cancelled" ก๊วนที่ยังเป็น `open` / `draft` / `ready_to_book`
จะหลุดเข้ามาได้ — นั่นคือก๊วนที่ยังไม่ได้สนามด้วยซ้ำ แต่กลับเรียกเก็บค่าลูกได้

เรื่องนี้เคยเป็นบั๊กจริงใน LSN-0020 และถูกจับได้ตอน review จึงเขียนเป็นกติกาไว้ตรงนี้

### 3. คนที่จ่ายรอบแรกไปแล้ว โดนเรียกเก็บเพิ่มได้ไหม?

**เสนอ: ได้ แต่เป็นหนี้ก้อนใหม่ ไม่ใช่การแก้ยอดเดิม**

ข้อนี้ดูขัดกับกติกาของ LSN-0021 ที่เขียนไว้ว่า *"settlement ไม่แตะคนที่จ่ายแล้ว
การเรียกเก็บย้อนหลังจากคนที่เคลียร์แล้วคือการให้ยืมเงินย้อนกลับ"* — แต่จริง ๆ ไม่ขัด
ถ้าอ่านกติกานั้นให้ตรงความหมาย

กติกาเดิมห้าม **เขียนทับยอดที่คนหนึ่งตกลงจ่ายไปแล้ว** ไม่ได้ห้ามขอเงินเพิ่ม
ความต่างอยู่ตรงนี้:

- ❌ ผิดกติกา: เคยจ่าย ฿250 แล้ว → แก้ `amount_due_thb` เป็น ฿280 ย้อนหลัง
- ✅ ตรงกติกา: เคยจ่าย ฿250 แล้ว (ยอดนั้นแตะต้องไม่ได้) → มีรายการใหม่ "ค่าลูก ฿30" แยกอีกบรรทัด

**ผลที่ตามมาในการออกแบบ:** รายการเพิ่มเติมต้อง **ไม่** ยุ่งกับ
`session_participants.amount_due_thb` และไม่แก้ `payments` แถวเดิมเลย
มันสร้าง `payments` แถวใหม่ของตัวเอง ซึ่งแปลว่า pgTAP ของ LSN-0021 ที่ปักกติกา
"ที่นั่งที่จ่ายแล้วต้องไม่ถูกแตะ" จะยังเขียวอยู่ **โดยไม่ต้องแก้เทสเลย** — ถ้ามันแดง
แปลว่าออกแบบผิด นั่นคือสัญญาณที่อยากได้

### 4. ผู้เล่นรับเชิญที่จ่ายเงินสดแล้ว?

**เสนอ: บันทึกส่วนแบ่งไว้บนใบสรุป แต่ไม่สร้างหนี้ ไม่ทวง ไม่หักเครดิต**

ตรงกับที่ LSN-0022 วางไว้ทั้งหมด: ผู้เล่นรับเชิญไม่มีบัญชี จึงไม่มีที่ให้แจ้งเตือน
และเงินสดของเขาไม่เคยผ่านระบบ

ผู้จัดเห็นบนหน้าจอว่า "พี่ต้น ค่าลูก ฿30 — เก็บเอง" เหมือนที่ตอนนี้เห็นคำเตือนว่า
เงินสดผู้เล่นรับเชิญคืนผ่านระบบไม่ได้

> **หมายเหตุลำดับงาน:** ข้อนี้ต้องรอ LSN-0022 merge ก่อน ตอนเขียน spec นี้
> LSN-0022 ยังอยู่ใน review (14 commit ยังไม่ merge)

### 5. ไม่จ่ายรายการเพิ่มเติม → หักเครดิตไหม?

**เสนอ: ไม่หัก ใน v1**

เหตุผลไม่ใช่ความใจดี แต่เป็นช่องโหว่: ตอนนี้เครดิตถูกหักได้จากสองเหตุการณ์ที่
**ระบบเป็นคนตัดสิน** เท่านั้น — `no_show_unpaid` (ไม่เช็คอินและไม่จ่าย) และเหตุการณ์
รอบ pay-later ส่วนรายการเพิ่มเติมนั้น **ผู้จัดพิมพ์เองทั้งชื่อและจำนวนเงิน**

ถ้าปล่อยให้มันหักเครดิตได้ ผู้จัดคนหนึ่งจะสร้างรายการ "ค่าไม้ ฿5,000" ลงชื่อคนที่
ทะเลาะด้วย รอให้เลยกำหนด แล้วคะแนนของคนนั้นก็ร่วง — พังทั้งระบบเครดิตที่ LSN-0019
สร้างมาเพื่อเป็นเกณฑ์ให้สิทธิ์จ่ายทีหลัง

ยังทวงได้ตามปกติ (แจ้งเตือนผ่าน `notify_user`) แค่ไม่แตะคะแนน
ถ้าวันหนึ่งอยากให้หักจริง ควรมีเพดานต่อรายการและต้องให้ผู้เล่นยืนยันก่อน
ซึ่งเป็นงานคนละใบ

## Design

### ตารางใหม่

```
session_charges
  id                uuid pk
  session_id        uuid → sessions
  label             text          ชื่อรายการที่ผู้จัดพิมพ์ เช่น "ค่าลูกแบด 3 ลูก"
  amount_thb        integer       ยอดรวมของบรรทัดนี้ ไม่ใช่ยอดต่อคน
  split_mode        enum(all, named)
  created_by        uuid → profiles
  created_at        timestamptz
  voided_at         timestamptz   ลบแล้วไม่หายไปจากประวัติ

session_charge_shares
  id                uuid pk
  charge_id         uuid → session_charges
  participant_id    uuid → session_participants
  amount_thb        integer       ส่วนแบ่งของคนนี้ คำนวณตอนสร้าง
  payment_id        uuid → payments   null สำหรับผู้เล่นรับเชิญ
```

**ทำไมเก็บส่วนแบ่งเป็นแถว ไม่คำนวณสด:** ยอดที่คนหนึ่งถูกเรียกเก็บต้องไม่เปลี่ยน
เมื่อมีคนอื่นถูกเพิ่มหรือลบออกจากก๊วนทีหลัง ถ้าคำนวณสดทุกครั้ง คนที่จ่ายไปแล้ว ฿30
จะกลายเป็นค้าง ฿5 เมื่อมีคนที่ 7 เข้ามา ซึ่งเป็นบั๊กแบบเดียวกับที่กติกาข้อ 3 ห้ามไว้

### การปัดเศษ

ใช้กติกาเดียวกับ LSN-0021: **ปัดขึ้น ผู้จัดรับส่วนต่าง**
฿100 หาร 3 คน = ฿34 ต่อคน เก็บได้ ฿102 ผู้จัดได้เกิน ฿2
ดีกว่าเก็บขาดแล้วผู้จัดต้องออกเอง และเป็นพฤติกรรมที่ผู้ใช้เจอมาแล้วจาก LSN-0021

### ความสัมพันธ์กับ `shuttle_cost_thb`

**เสนอ: ยังไม่ย้าย ใน v1**

ทางที่สะอาดกว่าคือย้าย `shuttle_cost_thb` เข้ามาเป็นบรรทัดแรกของตารางนี้
แล้วมีที่เก็บค่าใช้จ่ายที่เดียว แต่มันแปลว่าต้องแก้ `settle_session_costs`
ซึ่งมี pgTAP ปักไว้ (6 ข้อบน main, 8 หลัง LSN-0022) และต้อง migrate ข้อมูลเดิม

v1 ปล่อยให้อยู่กันคนละที่: `shuttle_cost_thb` คือค่าใช้จ่ายที่รู้ตอนสรุป
`session_charges` คือค่าใช้จ่ายที่นึกออกทีหลัง ใบสรุปรวมสองที่นี้เข้าด้วยกัน

**บันทึกไว้เป็นหนี้ทางเทคนิค** ว่าถ้าวันหนึ่งผู้ใช้สับสนว่าจะกรอกค่าลูกตรงไหน
นั่นคือสัญญาณว่าถึงเวลาย้าย

## Acceptance criteria

- [ ] ผู้จัดสร้างรายการพร้อมชื่อและยอดรวมได้ เลือกได้ว่าหารทั้งก๊วนหรือลงเฉพาะคน
- [ ] เลือก `named` แล้วเลือกผู้เล่นได้มากกว่าหนึ่งคน
- [ ] ส่วนแบ่งถูกคำนวณตอนสร้างและเก็บเป็นแถว ไม่เปลี่ยนเมื่อสมาชิกก๊วนเปลี่ยน — ปักด้วยเทส
- [ ] `amount_due_thb` และ `payments` แถวเดิมของทุกคน **ไม่ถูกแตะ** — ปักด้วยเทส
- [ ] pgTAP ของ LSN-0021 ยังเขียวโดยไม่ต้องแก้ — 6 ข้อบน main วันนี้
      และ 8 ข้อหลัง LSN-0022 merge (ตั๋วนั้นเพิ่มสองข้อเรื่องตัวหารของผู้เล่นรับเชิญ)
- [ ] สร้างรายการในก๊วนที่ยังไม่ `booked` / `completed` ถูกปฏิเสธ — ปักด้วยเทส
- [ ] ผู้เล่นรับเชิญไม่มี `payments` ไม่เข้าคิวทวง ไม่มี `credit_events` — ปักด้วยเทส
- [ ] รายการเพิ่มเติมที่ค้างไม่ทำให้เกิด `credit_events` เลย — ปักด้วยเทส
- [ ] ลบรายการแล้ว `payments` ที่ยัง `pending` ถูกทำเป็น `expired` ไม่ใช่ลบทิ้ง
- [ ] ทุกการสร้างและลบเขียน `audit_logs`

## Validation

- `npm run lint`, `npx tsc --noEmit`, `npm test` ผ่าน
- `npm run test:db` ผ่าน รวมข้อใหม่ของตั๋วนี้ และข้อเดิมของ LSN-0019/0020/0021/0022 ไม่แดง
- migration apply จาก `npm run db:reset` ได้
- ไม่มี UI ที่กดแล้วไม่ทำอะไร ปุ่มไหนใช้ไม่ได้ต้อง disabled พร้อมเหตุผล

## Open questions

- **ชื่อรายการมี preset ไหม** เช่น "ค่าลูกแบด" / "ค่าไม้" / "ค่าน้ำ" ให้กดเลือกเร็ว ๆ
  แทนการพิมพ์ทุกครั้ง — ถ้ามี ควรผูกกับ `sports.slug` หรือเป็นรายการกลางชุดเดียว
- **เพดานยอดต่อรายการ** ควรมีไหม ตอนนี้ผู้จัดพิมพ์เลขอะไรก็ได้
  ไม่มีเพดานแปลว่าพิมพ์ ฿50,000 ได้ ซึ่งน่าจะเป็นการพิมพ์ผิดมากกว่าเจตนา
- **แจ้งเตือนตอนไหน** สร้างรายการแล้วแจ้งทันที หรือรวมแจ้งครั้งเดียวตอนผู้จัดกด "ส่งเรียกเก็บ"
  แบบหลังดีกว่าถ้าผู้จัดสร้างหลายรายการติดกัน จะได้ไม่ยิงแจ้งเตือนรัวสี่รอบ
