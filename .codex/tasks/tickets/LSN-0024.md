# 🟢 LSN-0024 — รายการเก็บเงินเพิ่มหลังจบก๊วน

**Type:** Feature · **Phase:** 9 · **Status:** Backlog
**Spec:** `.codex/specs/extra-charges.md`
**Depends on:** LSN-0021 (ตัวหารและกติกาห้ามแตะคนที่จ่ายแล้ว), LSN-0022 (ผู้เล่นรับเชิญ — **ยังอยู่ใน review**)

## Goal

ผู้จัดก๊วนสร้างรายการค่าใช้จ่ายเพิ่มเติมหลังเล่นจบได้หลายบรรทัด เช่น ค่าลูกแบดที่ซื้อระหว่างเล่น
หรือค่าไม้ที่บางคนยืม แล้วระบบเรียกเก็บให้ แทนที่ผู้จัดจะต้องพิมพ์ทวงในกลุ่ม LINE เอง

## Context

LSN-0021 หารค่าใช้จ่ายตามคนที่มาจริงได้แล้ว แต่เก็บค่าลูกไว้ในช่องเดียวชื่อ
`sessions.shuttle_cost_thb` ซึ่งตั้งชื่อไม่ได้ แยกประเภทไม่ได้ และหารเท่ากันทุกคนเสมอ
ทั้งที่ค่าไม้ควรลงเฉพาะคนที่ยืม

ตั๋วนี้เพิ่มรายการค่าใช้จ่ายแบบหลายบรรทัด โดย **ไม่แตะ** `shuttle_cost_thb` และ
**ไม่แตะ** ยอดที่แต่ละคนตกลงจ่ายไปแล้ว

## Scope

- ตาราง `session_charges` (บรรทัดค่าใช้จ่าย) และ `session_charge_shares` (ส่วนแบ่งรายคน)
- RPC สร้าง ส่งเรียกเก็บ และลบรายการ เฉพาะผู้จัดก๊วน
- ส่วนแบ่งคำนวณตอนสร้างและเก็บเป็นแถว ไม่คำนวณสดทีหลัง
- แต่ละบรรทัดเลือก split ของตัวเอง: `all` (หารคนที่นับในตัวหารตามกติกา LSN-0021) หรือ `named` (เฉพาะคนที่เลือก)
- UI ฝั่งผู้จัดสำหรับสร้าง ดูตัวอย่างว่าใครโดนเท่าไร ส่งเรียกเก็บ และลบรายการ
- ผู้เล่นเห็นยอดที่ตัวเองถูกเรียกเก็บ และจ่ายผ่านช่องทางเดิม

## Non-goals

- ไม่ทำระบบสต็อกอุปกรณ์ ไม่ผูกกับสินค้าของสนาม
- ไม่ให้ผู้เล่นสร้างรายการเอง
- ไม่ทำการคืนเงินรายการเพิ่มเติม — พิมพ์ผิดให้ลบบรรทัดแล้วสร้างใหม่
- ไม่ย้าย `shuttle_cost_thb` เข้าตารางใหม่ในรอบนี้ (บันทึกเป็นหนี้ทางเทคนิค)
- ไม่แตะ `budget_per_person_thb` ซึ่งเป็นยอดที่ผู้เล่นตกลงตอนกดเข้าร่วม

## Decisions from the spec

ห้าข้อนี้ตัดสินไว้ใน spec แล้ว พร้อมเหตุผล — ถ้าจะเปลี่ยนต้องเปลี่ยนที่ spec ก่อน

1. **split เลือกได้ต่อบรรทัด** (`all` / `named`) เพราะค่าไม้ไม่ควรหารทั้งก๊วน
   นี่คือเหตุผลที่ฟีเจอร์นี้ไม่ใช่แค่เพิ่มช่องใน `settle_session_costs` ซึ่ง `split_mode`
   ของมันเป็นของทั้งก๊วน ไม่ใช่ของรายบรรทัด
2. **สร้างได้เฉพาะก๊วน `booked` หรือ `completed`** — allowlist ไม่ใช่ denylist
   ด้วยเหตุผลเดียวกับบั๊กที่เคยเจอใน LSN-0020: denylist ปล่อยให้ `open` / `draft` /
   `ready_to_book` หลุดเข้ามา ซึ่งเป็นก๊วนที่ยังไม่ได้สนามด้วยซ้ำ
3. **เรียกเก็บจากคนที่จ่ายแล้วได้ แต่เป็นหนี้ก้อนใหม่** กติกาของ LSN-0021 ห้ามเขียนทับ
   ยอดที่ตกลงไปแล้ว ไม่ได้ห้ามขอเงินเพิ่ม ดังนั้นรายการเพิ่มเติมต้องสร้าง `payments`
   แถวใหม่ ห้ามแตะ `amount_due_thb` หรือ `payments` แถวเดิม
4. **ผู้เล่นรับเชิญ** บันทึกส่วนแบ่งให้เห็นบนหน้าจอ แต่ไม่สร้าง `payments`
   ไม่เข้าคิวทวง ไม่แตะเครดิต — ตรงกับที่ LSN-0022 วางไว้
5. **ไม่หักเครดิต** เพราะผู้จัดพิมพ์ชื่อและยอดเอง ถ้าหักได้จะกลายเป็นช่องให้สร้างรายการ
   ปลอมลงชื่อคนที่ไม่ถูกกัน แล้วทำคะแนนเขาร่วง — พังระบบเครดิตที่ LSN-0019 สร้างไว้
   เป็นเกณฑ์ให้สิทธิ์จ่ายทีหลัง

## Open Questions — ตัดสินครบแล้ว 11 ก.ย.

### 1. ชื่อรายการ → พิมพ์เอง แต่มีชิปกดเติมเร็ว ไม่มีตาราง

เก็บใน DB เป็น free text เหมือนเดิม แต่ UI มีชิปให้กดเติมช่องข้อความ ตามกีฬาของก๊วนนั้น
เช่นแบดมินตันขึ้น "ค่าลูกแบด · ค่าไม้ · ค่าคอร์ตเพิ่ม" ฟุตบอลขึ้น "ค่าเสื้อ · ค่าน้ำ"

ชิปเป็น `Record<sportSlug, string[]>` ฮาร์ดโค้ดใน `src/i18n/th.ts`
**ไม่มีตารางใหม่ ไม่มี migration ไม่มี API** ค่าที่บันทึกยังเป็นข้อความที่ผู้จัดยืนยัน

เหตุผล: non-goal ของตั๋วนี้เขียนไว้เองว่า "ไม่ทำระบบสต็อกอุปกรณ์ ไม่ผูกกับสินค้าของสนาม"
ตารางรายการสำเร็จรูปคือก้าวแรกของระบบสต็อก แล้วจะตามมาด้วยคำถามว่าใครแก้ได้
ลบแล้วของเก่าเป็นอะไร แปลภาษายังไง ชิปฮาร์ดโค้ดให้ผลทาง UX เกือบเท่ากันโดยไม่เปิดประตูนั้น
และเปลี่ยนทีหลังได้ด้วยการแก้ไฟล์เดียว มี `sports` อยู่ 6 แถวรวม `custom` จึงครอบคลุมครบ

### 2. เพดานยอด → สองชั้น คนละหน้าที่กัน

**ชั้นฐานข้อมูล:** `check (amount_thb > 0 and amount_thb <= 100000)`

- `> 0` ไม่ใช่ `>= 0` — รายการ ฿0 ไม่มีความหมาย และจะสร้าง payment ฿0
  กับแจ้งเตือนคนที่ไม่ได้ติดเงิน
- `<= 100000` เป็นเพดานกันพิมพ์ผิด ไม่ใช่เพดานเชิงธุรกิจ ฿100,000 สำหรับรายการเดียว
  ในก๊วนสมัครเล่นเป็นไปไม่ได้ มันจับ "เผลอใส่ศูนย์เกิน" โดยไม่เคยขวางยอดจริง

**ชั้น UI:** ยอดเกิน ฿2,000 ต้องกดยืนยันอีกครั้ง โดยกล่องยืนยัน**แสดงยอดต่อคน**
("฿5,000 หาร 8 คน = คนละ ฿625 ยืนยันไหม") ตรงนี้คือที่ที่พิมพ์ผิดถูกจับจริง
เพราะคนมองเลขต่อคนแล้วรู้ทันที ส่วน check ใน DB เป็นตาข่ายชั้นสุดท้ายเผื่อมีใครเรียก RPC ตรง

**ความไม่สม่ำเสมอที่ตั้งใจ:** ตรวจแล้วว่าทั้งสคีมาไม่มีคอลัมน์เงินไหนมีเพดานเลย
มีแต่ `>= 0` การใส่เพดานเฉพาะตารางนี้จึงต่างจากที่อื่น — แต่ตารางนี้ต่างจริง
เพราะ**ผู้จัดพิมพ์เลขเองแล้วมันกลายเป็นหนี้ของคนอื่นทันที** ต่างจาก
`budget_per_person_thb` ที่ผู้เล่นเห็นและกดยอมรับก่อนเข้าร่วม

### 3. แจ้งเตือน → มีขั้นตอน "ส่งเรียกเก็บ" แยกต่างหาก

สร้างรายการแล้ว **ยังไม่แจ้งใคร และยังไม่มีหนี้เกิดขึ้น** ผู้จัดสร้างได้หลายบรรทัด
ดูว่าใครโดนเท่าไร แล้วค่อยกดส่งครั้งเดียว

**ผลต่อสคีมาและลำดับการทำงาน:**

- `session_charges.notified_at timestamptz` — null แปลว่ายังเป็นฉบับร่าง
- `session_charge_shares` สร้างตั้งแต่ตอนสร้างรายการ เพื่อให้ผู้จัด**เห็นล่วงหน้า**
  ว่าใครโดนเท่าไรก่อนตัดสินใจส่ง
- **`payments` สร้างตอนกดส่งเท่านั้น** ไม่ใช่ตอนสร้างรายการ
  เพราะหนี้ไม่ควรโผล่ในหน้าจอผู้เล่นก่อนที่ผู้จัดจะตั้งใจเรียกเก็บ
- แจ้งเตือน **หนึ่งครั้งต่อคน** สรุปยอดรวมของทุกบรรทัดที่ส่งรอบนั้น ไม่ใช่ต่อบรรทัด
  (ตรวจแล้วว่าระบบยังไม่มีกลไกรวมแจ้งเตือนเลย `notify_user` มี 9 call site แต่ละที่ยิงทีละแถว
  ตัวนี้จะเป็นตัวแรกที่รวม)

**สิ่งที่ได้มาฟรีและมีค่ากว่าที่คิด:** รายการที่พิมพ์ผิดลบทิ้งได้เงียบ ๆ ก่อนมีใครรู้
กล่องยืนยันในข้อ 2 จึงไม่ใช่ด่านสุดท้าย ถ้ามันหลุดมายังมีจังหวะให้แก้

**ต้นทุน:** หนึ่งคอลัมน์ หนึ่ง RPC หนึ่งปุ่ม ถูกกว่าการต้องอธิบายให้ผู้เล่นแปดคนฟัง
ว่าทำไมมีหนี้โผล่มาแล้วหายไป
