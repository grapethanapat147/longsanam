# 🟢 LSN-0029 — ทัวร์นาเมนต์ + สมัครเป็นทีม + คืนเงินเมื่อไม่ครบ

**Type:** Feature · **Phase:** 10 · **Status:** Review
**Spec:** `.codex/specs/tournaments.md`
**Depends on:** LSN-0027 และ LSN-0026 — **merge เข้า main ครบแล้ว 17 ก.ย. 2569**

## Goal

ก๊วนที่เล่นประจำสร้างทัวร์นาเมนต์ได้ ก๊วนอื่นสมัครผ่านลิงก์เดียวที่แชร์เข้า LINE
และถ้าทีมไม่ครบขั้นต่ำภายในกำหนด **ทุกก๊วนได้เงินคืนเต็ม**

นี่คือหัวใจของ flow ทัวร์นาเมนต์ และเป็นตั๋วที่ทำให้พาดหัวของโปรดักต์
(`docs/product-concept.md`) เป็นจริงเป็นครั้งแรก

## Context

ของที่ flow นี้พึ่งมีครบแล้วหลัง LSN-0026:

| ของที่ต้องมี | สถานะ |
| --- | --- |
| ก๊วนที่คงอยู่ข้ามครั้ง + สมาชิก | **มีแล้ว** — `groups`, `group_members` |
| ลิงก์เชิญรูปแบบเดียวกับนัด | **มีแล้ว** — `generate_group_code()` และ `/g/[code]` |
| กลไกเก็บเงิน หารเงิน คืนเงิน | **มีแล้ว** — ตั้งแต่ LSN-0019 ถึง LSN-0024 |
| คำว่า "ก๊วน" หมายถึงกลุ่มคน | **มีแล้ว** — LSN-0027 |

**สิ่งที่ตั๋วนี้เพิ่มคือประตูบานที่สาม** — เดิมประตูมีสองบาน คน + เงิน
ทัวร์นาเมนต์ต้องการ **ทีม + เงิน + คอร์ต** และกลไกคืนเงินเมื่อไม่ครบ
ใช้ของที่มีอยู่แล้วทั้งดุ้น ไม่ต้องคิดใหม่

## Scope

- ตาราง `tournaments` และ `tournament_teams`
- สร้างทัวร์นาเมนต์: วัน เวลา ค่าสมัครต่อก๊วน ขั้นต่ำ/สูงสุดจำนวนทีม รุ่นที่เปิดรับ
- ลิงก์สมัครแบบเดียวกับก๊วนและนัด — แชร์เข้า LINE แล้วกดได้เลย
- ก๊วนอื่นสมัครเข้าแข่ง โดย**ผู้จัดก๊วนจ่ายค่าสมัครก้อนเดียวต่อทีม**
- ประตูสามบาน: ทีมครบขั้นต่ำ · เงินครบ · คอร์ตยืนยันแล้ว
- **ครบไม่ทัน `registration_deadline` → คืนเงินเต็มทุกก๊วนอัตโนมัติ**
- หน้ารายการทัวร์นาเมนต์ · หน้าทัวร์นาเมนต์หนึ่งงาน · หน้ารับสมัคร

## Non-goals

- **ไม่บันทึกผลแมตช์** — LSN-0030
- **ไม่ทำคะแนนฝีมือและไม่กรองรุ่นอัตโนมัติ** — LSN-0031
  ตั๋วนี้เก็บ `tier` ที่ผู้จัด *ประกาศ* ว่าเปิดรับ แต่ยังไม่บังคับใครทั้งนั้น
- ไม่ทำเพื่อนและการประเมินความประทับใจ — LSN-0032
- ไม่ทำ bracket หรือตารางแข่งอัตโนมัติ — spec ระบุเป็น non-goal
- ไม่ทำเงินรางวัลผ่านระบบ — เป็นเรื่องกฎหมายคนละเรื่อง
- ไม่แตะ `player_credit` ไม่ว่าทางใด

## Decisions — มาจาก spec แล้ว ผูกพันตั๋วนี้

### 1. สมัคร**เป็นก๊วน** ไม่ใช่รายคน

ก๊วนคือหน่วยที่จ่ายเงินและเป็นเจ้าของชื่อเสียง ส่วนใครว่างไม่ว่างเป็นรายละเอียด
หน้างานที่เปลี่ยนได้จนถึงกำหนด

### 2. ค่าสมัคร — ผู้จัดก๊วนจ่ายก้อนเดียว แล้วหารกันเองในก๊วน

**ไม่ต้องสร้างอะไรใหม่เลย** ค่าสมัครกลายเป็นค่าใช้จ่ายก้อนหนึ่งที่กลไกเก็บเงิน
ของก๊วนจัดการอยู่แล้ว บัญชีฝั่งทัวร์นาเมนต์จึงเป็น **หนึ่งทีม หนึ่งการจ่าย**

→ ประตู "เงินครบ" ของทัวร์นาเมนต์นับ **การจ่ายระดับทีม ไม่ใช่รายคน**

### 3. ไม่ครบตามกำหนด = คืนเต็ม ไม่ใช่เลื่อน

คืนเงินเต็มทุกก๊วนเมื่อถึง `registration_deadline` แล้วทีมไม่ถึงขั้นต่ำ
เพราะนี่คือคำสัญญาเดียวกับที่โปรดักต์ให้ไว้ตั้งแต่ระดับนัด — **ไม่มีใครต้อง
รับความเสี่ยงคนเดียว**

### 4. สถานะใช้รูปเดียวกับนัด

`draft → open → ready → booked → completed` (+ `cancelled`)
ผู้ใช้เรียนรู้ครั้งเดียวใช้ได้ทั้งสองระดับ และ state machine ที่มีอยู่แล้ว
ใน `src/lib/domain/state-machines.ts` เป็นแบบแผนให้ลอกได้

### 5. `tier` เก็บเป็น enum ที่เรียงลำดับได้ — **N · S · P · C · B · A**

เก็บให้เทียบมากกว่า/น้อยกว่าได้ตั้งแต่ตอนนี้ แม้ตั๋วนี้ยังไม่บังคับใช้
เพื่อไม่ต้องย้ายข้อมูลตอน LSN-0031

**และต้องประกาศให้ชัดในหน้าจอว่าแพลตฟอร์มเลือกลำดับนี้แบบเดียว**
ไม่อ้างว่าเป็นมาตรฐานกลางของวงการ เพราะแต่ละสนามแยกย่อยไม่เหมือนกัน

## Design

```sql
create type public.tournament_tier as enum ('N', 'S', 'P', 'C', 'B', 'A');

create table public.tournaments (
  id                    uuid primary key default gen_random_uuid(),
  public_code           text unique,              -- ลิงก์สมัคร รูปแบบเดียวกับ /g/ และ /s/
  host_group_id         uuid not null references public.groups(id),
  title                 text not null,
  starts_at             timestamptz not null,
  ends_at               timestamptz not null,
  registration_deadline timestamptz not null,
  min_teams             integer not null,
  max_teams             integer,
  entry_fee_thb         integer not null,
  tier                  public.tournament_tier not null,
  status                public.tournament_status not null default 'draft',
  created_by            uuid not null references public.profiles(id),
  created_at            timestamptz not null default now(),
  updated_at            timestamptz not null default now()
);

create table public.tournament_teams (
  tournament_id uuid not null references public.tournaments(id) on delete cascade,
  group_id      uuid not null references public.groups(id) on delete cascade,
  joined_at     timestamptz not null default now(),
  primary key (tournament_id, group_id)
);

-- ตารางเงินของตัวเอง ไม่แตะ payments เลย — ดู Open Questions ข้อ 1
create table public.tournament_team_payments (
  id            uuid primary key default gen_random_uuid(),
  tournament_id uuid not null,
  group_id      uuid not null,
  paid_by       uuid not null references public.profiles(id),
  amount_thb    integer not null check (amount_thb > 0),
  status        public.payment_status not null default 'pending',
  provider      text not null,
  provider_ref  text,
  idempotency_key text not null unique,
  paid_at       timestamptz,
  refunded_at   timestamptz,
  created_at    timestamptz not null default now(),
  foreign key (tournament_id, group_id)
    references public.tournament_teams (tournament_id, group_id) on delete cascade
);

-- หนึ่งทีม หนึ่งการจ่ายที่ยังไม่ปิด — บทเรียนจาก payments_one_live_per_participant
create unique index tournament_team_one_live_payment
  on public.tournament_team_payments (tournament_id, group_id)
  where status in ('pending', 'paid');
```

**PK เป็น `(tournament_id, group_id)`** ด้วยเหตุผลเดียวกับ `group_members` —
ก๊วนเดียวสมัครซ้ำไม่ได้โดยโครงสร้าง ไม่ต้องพึ่งการตรวจในโค้ด

## Open Questions — ตัดสินครบแล้ว 17 ก.ย. 2569

### 1. ค่าสมัครไหลผ่านอะไร → **ตารางของตัวเอง ไม่แตะ `payments`**

`tournament_team_payments` แยกต่างหาก และ **ห้ามเพิ่มคอลัมน์ให้ `payments`
เพื่อรองรับทัวร์นาเมนต์**

**เหตุผลที่ตัดสินแบบนี้ ไม่ใช่เรื่องรสนิยม แต่มาจากตัวเลข** — ตรวจสคีมาจริงแล้ว

| ข้อเท็จจริง | ผล |
| --- | --- |
| `payments.session_id` | **NOT NULL** |
| `payments.participant_id` | **NOT NULL** |
| `refunds.payment_id` และ `refunds.session_id` | **NOT NULL ทั้งคู่** |
| จุดที่อ้างถึง `payments` ใน migration | **73 จุด ใน 10 ไฟล์** |

การเก็บค่าสมัครใน `payments` แปลว่าต้องทำ **สองคอลัมน์ NOT NULL ให้เป็น
nullable** ซึ่งตาม Definition of Done ที่เพิ่งเพิ่มเข้าไปหลัง LSN-0024
บังคับให้ต้องไล่ผู้อ่านของข้อจำกัดเดิม **ทั้ง 73 จุด** — บนตารางที่เพิ่งผลิต
บั๊กกินเงินผู้ใช้มาหมาด ๆ และเพื่อฟีเจอร์ที่ payment provider ยังไม่มีอยู่จริงด้วยซ้ำ

**และรูปของเงินสองก้อนนี้ไม่เหมือนกันเลย** ค่าสมัครคือ *หนึ่งทีม หนึ่งการจ่าย*
ไม่มีที่นั่ง ไม่มีเช็คอิน ไม่มีจ่ายทีหลัง ไม่มีการหารรายหัว การใช้ตารางร่วมกัน
จึงไม่ได้อะไรกลับมานอกจากความผูกพัน

**การคืนเงินก็เขียนใหม่ได้ง่ายกว่าใช้ของเดิม** เพราะทัวร์นาเมนต์คืนแบบ
**ทั้งหมดหรือไม่คืนเลย** ไม่มีนโยบายตามเวลาเหลือแบบระดับนัด ตรรกะจึงสั้นกว่ามาก
และไม่ต้องไปยุ่งกับ `cancel_participation()` ที่ซับซ้อนอยู่แล้ว

> **ข้อนี้ไม่ได้แปลว่าจะไม่มีวันรวมกัน** ถ้าวันหนึ่งมี payment provider จริง
> แล้วพบว่าสองทางต้องใช้ provider เดียวกัน การรวมทำได้ตอนนั้นโดยมีของจริง
> ให้ดู ดีกว่าทำตอนนี้โดยเดา

### 2. คอร์ตมาก่อนหรือหลัง → **ขนานกัน ไม่มีอันไหนกั้นอันไหน**

สามประตูเป็นอิสระต่อกัน ทัวร์นาเมนต์ไปสถานะ `ready` เมื่อ **ครบทั้งสามพร้อมกัน**
เจ้าภาพยืนยันคอร์ตเมื่อไรก็ได้ ก่อนหรือหลังเปิดรับทีมก็ได้

**เหตุผลอยู่ใน `docs/product-concept.md` หัวข้อ Insight ซึ่งเขียนไว้ว่า**

> เงินกับสนามต้องถูกตัดสิน **พร้อมกัน ไม่ใช่ตามลำดับ**

การบังคับลำดับคือการทำสิ่งที่โปรดักต์ตั้งขึ้นมาเพื่อแก้ ถ้าบังคับให้หาคอร์ตก่อน
เจ้าภาพต้องแบกความเสี่ยงคนเดียวว่าจะมีทีมมาไหม ถ้าบังคับให้เปิดรับทีมก่อน
ทีมต้องจ่ายโดยไม่รู้ว่าจะมีที่เล่นไหม **ทั้งสองแบบคือทางตันเดิมที่ใหญ่ขึ้นหนึ่งระดับ**

`registration_deadline` เป็นตัวปิดความเสี่ยงแทนการบังคับลำดับ — ถึงกำหนดแล้ว
ประตูไหนยังไม่ครบ คืนเงินเต็มทุกทีม ไม่มีใครค้างอยู่กับความไม่แน่นอน

`confirm_court_manually()` จาก LSN-0025 ใช้ได้ตรง ๆ ไม่ต้องรอสนามพันธมิตร

### 3. เจ้าภาพ → **นับเป็นหนึ่งทีมอัตโนมัติ และจ่ายค่าสมัครเหมือนทีมอื่น**

ตอนสร้างทัวร์นาเมนต์ ระบบใส่แถว `tournament_teams` ให้ก๊วนเจ้าภาพทันที
และแถวนั้นต้องมีการจ่ายเหมือนทุกทีมก่อนประตู "เงินครบ" จะเปิด

**เหตุผลที่หนึ่ง — flow ต้นฉบับบอกไว้เอง** ที่เขียนว่า *"ต้องการอีก 3 ก๊วนมาแจม"*
คำว่า **อีก** แปลว่าเจ้าภาพนับเป็นหนึ่งแล้ว ขั้นต่ำ 4 ทีมจึงหมายถึงชวนเพิ่ม 3

**เหตุผลที่สอง และเป็นข้อที่หนักกว่า — กรณียกเว้นในโค้ดเรื่องเงินคือที่ที่บั๊กอยู่**
ถ้าเจ้าภาพไม่จ่าย การนับ "ทุกทีมจ่ายแล้ว" จะมีเงื่อนไขพิเศษว่า
*ยกเว้นเจ้าภาพ* ติดอยู่ตลอดไป ซึ่งเป็นรูปเดียวกับที่ LSN-0024 พังมาแล้ว
ตอนที่ `payments` มีสองความหมายในตารางเดียว **ประตูที่นับทุกทีมเท่ากัน
ไม่มีข้อยกเว้น คือประตูที่เขียนเทสได้และอ่านออก**

**เหตุผลที่สาม** ค่าสมัครคือส่วนแบ่งค่าคอร์ตของทีมนั้น และทีมเจ้าภาพก็ลงเล่น
ใช้คอร์ตเหมือนกัน เจ้าภาพที่ไม่จ่ายคือการรับส่วนลดที่ทีมอื่นออกให้

**ถ้าเจ้าภาพอยากได้ส่วนลดจริง ๆ** เขาตั้งค่าสมัครเองได้อยู่แล้ว ซึ่งเป็นการ
ตัดสินใจของเขา ไม่ใช่กติกาที่ฝังอยู่ในระบบ

**สิ่งที่ตั๋วนี้จะไม่ทำ และบันทึกไว้ให้ชัด:** ไม่ทำระบบ *จ่ายเงินออก* ให้เจ้าภาพ
เงินค่าสมัครไม่ได้ไหลจากระบบไปหาเจ้าภาพในตั๋วนี้ เพราะนั่นเปิดคำถาม
"การถือเงินของคนอื่น" ที่ `docs/product-concept.md` ระบุว่ายังไม่ตัดสิน
ตั๋วนี้จบที่ **เก็บได้ครบ หรือคืนเต็ม** เท่านั้น
