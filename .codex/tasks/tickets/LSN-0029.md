# 🟢 LSN-0029 — ทัวร์นาเมนต์ + สมัครเป็นทีม + คืนเงินเมื่อไม่ครบ

**Type:** Feature · **Phase:** 10 · **Status:** Backlog
**Spec:** `.codex/specs/tournaments.md`
**Depends on:** LSN-0027 และ LSN-0026 — **merge เข้า main ครบแล้ว 17 ก.ย. 2569**

## Goal

ก๊วนที่เล่นประจำสร้างทัวร์นาเมนต์ได้ ก๊วนอื่นสมัครผ่านลิงก์เดียวที่แชร์เข้า LINE
และถ้าทีมไม่ครบขั้นต่ำภายในกำหนด **ทุกก๊วนได้เงินคืนเต็ม**

นี่คือหัวใจของ flow ทัวร์นาเมนต์ และเป็นตั๋วที่ทำให้พาดหัวของโปรดักต์
(`docs/product-concept.md`) เป็นจริงเป็นครั้งแรก

## Context

ของที่ flow นี้พึ่งมีครบแล้วหลัง LSN-0026:

| ของที่ต้องมี | สถานะ |
| --- | --- |
| ก๊วนที่คงอยู่ข้ามครั้ง + สมาชิก | **มีแล้ว** — `groups`, `group_members` |
| ลิงก์เชิญรูปแบบเดียวกับนัด | **มีแล้ว** — `generate_group_code()` และ `/g/[code]` |
| กลไกเก็บเงิน หารเงิน คืนเงิน | **มีแล้ว** — ตั้งแต่ LSN-0019 ถึง LSN-0024 |
| คำว่า "ก๊วน" หมายถึงกลุ่มคน | **มีแล้ว** — LSN-0027 |

**สิ่งที่ตั๋วนี้เพิ่มคือประตูบานที่สาม** — เดิมประตูมีสองบาน คน + เงิน
ทัวร์นาเมนต์ต้องการ **ทีม + เงิน + คอร์ต** และกลไกคืนเงินเมื่อไม่ครบ
ใช้ของที่มีอยู่แล้วทั้งดุ้น ไม่ต้องคิดใหม่

## Scope

- ตาราง `tournaments` และ `tournament_teams`
- สร้างทัวร์นาเมนต์: วัน เวลา ค่าสมัครต่อก๊วน ขั้นต่ำ/สูงสุดจำนวนทีม รุ่นที่เปิดรับ
- ลิงก์สมัครแบบเดียวกับก๊วนและนัด — แชร์เข้า LINE แล้วกดได้เลย
- ก๊วนอื่นสมัครเข้าแข่ง โดย**ผู้จัดก๊วนจ่ายค่าสมัครก้อนเดียวต่อทีม**
- ประตูสามบาน: ทีมครบขั้นต่ำ · เงินครบ · คอร์ตยืนยันแล้ว
- **ครบไม่ทัน `registration_deadline` → คืนเงินเต็มทุกก๊วนอัตโนมัติ**
- หน้ารายการทัวร์นาเมนต์ · หน้าทัวร์นาเมนต์หนึ่งงาน · หน้ารับสมัคร

## Non-goals

- **ไม่บันทึกผลแมตช์** — LSN-0030
- **ไม่ทำคะแนนฝีมือและไม่กรองรุ่นอัตโนมัติ** — LSN-0031
  ตั๋วนี้เก็บ `tier` ที่ผู้จัด *ประกาศ* ว่าเปิดรับ แต่ยังไม่บังคับใครทั้งนั้น
- ไม่ทำเพื่อนและการประเมินความประทับใจ — LSN-0032
- ไม่ทำ bracket หรือตารางแข่งอัตโนมัติ — spec ระบุเป็น non-goal
- ไม่ทำเงินรางวัลผ่านระบบ — เป็นเรื่องกฎหมายคนละเรื่อง
- ไม่แตะ `player_credit` ไม่ว่าทางใด

## Decisions — มาจาก spec แล้ว ผูกพันตั๋วนี้

### 1. สมัคร**เป็นก๊วน** ไม่ใช่รายคน

ก๊วนคือหน่วยที่จ่ายเงินและเป็นเจ้าของชื่อเสียง ส่วนใครว่างไม่ว่างเป็นรายละเอียด
หน้างานที่เปลี่ยนได้จนถึงกำหนด

### 2. ค่าสมัคร — ผู้จัดก๊วนจ่ายก้อนเดียว แล้วหารกันเองในก๊วน

**ไม่ต้องสร้างอะไรใหม่เลย** ค่าสมัครกลายเป็นค่าใช้จ่ายก้อนหนึ่งที่กลไกเก็บเงิน
ของก๊วนจัดการอยู่แล้ว บัญชีฝั่งทัวร์นาเมนต์จึงเป็น **หนึ่งทีม หนึ่งการจ่าย**

→ ประตู "เงินครบ" ของทัวร์นาเมนต์นับ **การจ่ายระดับทีม ไม่ใช่รายคน**

### 3. ไม่ครบตามกำหนด = คืนเต็ม ไม่ใช่เลื่อน

คืนเงินเต็มทุกก๊วนเมื่อถึง `registration_deadline` แล้วทีมไม่ถึงขั้นต่ำ
เพราะนี่คือคำสัญญาเดียวกับที่โปรดักต์ให้ไว้ตั้งแต่ระดับนัด — **ไม่มีใครต้อง
รับความเสี่ยงคนเดียว**

### 4. สถานะใช้รูปเดียวกับนัด

`draft → open → ready → booked → completed` (+ `cancelled`)
ผู้ใช้เรียนรู้ครั้งเดียวใช้ได้ทั้งสองระดับ และ state machine ที่มีอยู่แล้ว
ใน `src/lib/domain/state-machines.ts` เป็นแบบแผนให้ลอกได้

### 5. `tier` เก็บเป็น enum ที่เรียงลำดับได้ — **N · S · P · C · B · A**

เก็บให้เทียบมากกว่า/น้อยกว่าได้ตั้งแต่ตอนนี้ แม้ตั๋วนี้ยังไม่บังคับใช้
เพื่อไม่ต้องย้ายข้อมูลตอน LSN-0031

**และต้องประกาศให้ชัดในหน้าจอว่าแพลตฟอร์มเลือกลำดับนี้แบบเดียว**
ไม่อ้างว่าเป็นมาตรฐานกลางของวงการ เพราะแต่ละสนามแยกย่อยไม่เหมือนกัน

## Design

```sql
create type public.tournament_tier as enum ('N', 'S', 'P', 'C', 'B', 'A');

create table public.tournaments (
  id                    uuid primary key default gen_random_uuid(),
  public_code           text unique,              -- ลิงก์สมัคร รูปแบบเดียวกับ /g/ และ /s/
  host_group_id         uuid not null references public.groups(id),
  title                 text not null,
  starts_at             timestamptz not null,
  ends_at               timestamptz not null,
  registration_deadline timestamptz not null,
  min_teams             integer not null,
  max_teams             integer,
  entry_fee_thb         integer not null,
  tier                  public.tournament_tier not null,
  status                public.tournament_status not null default 'draft',
  created_by            uuid not null references public.profiles(id),
  created_at            timestamptz not null default now(),
  updated_at            timestamptz not null default now()
);

create table public.tournament_teams (
  tournament_id uuid not null references public.tournaments(id) on delete cascade,
  group_id      uuid not null references public.groups(id) on delete cascade,
  payment_id    uuid references public.payments(id) on delete set null,
  joined_at     timestamptz not null default now(),
  primary key (tournament_id, group_id)
);
```

**PK เป็น `(tournament_id, group_id)`** ด้วยเหตุผลเดียวกับ `group_members` —
ก๊วนเดียวสมัครซ้ำไม่ได้โดยโครงสร้าง ไม่ต้องพึ่งการตรวจในโค้ด

## Open Questions — ต้องตัดสินก่อนเริ่ม

### 1. ค่าสมัครไหลผ่านอะไร

`src/lib/payments/` มีแค่ `mock.ts` (omise เว้นที่ไว้แต่ยังไม่ implement)
**เงินจริงไหลผ่านแอปไม่ได้เลยวันนี้** และค่าสมัครทัวร์นาเมนต์เป็นก้อนที่ใหญ่กว่า
ค่าที่นั่งรายคนหลายเท่า

จะใช้ตาราง `payments` เดิม (ซึ่งผูกกับ `participant_id` ของนัด) หรือสร้าง
ทางจ่ายของทีมแยก — ข้อนี้กระทบทั้งสคีมาและกลไกคืนเงิน

### 2. คอร์ตมาก่อนหรือหลังการเปิดรับทีม

ประตูบานที่สามคือคอร์ต แต่ลำดับยังไม่ตัดสิน:
เปิดรับทีมก่อนแล้วค่อยหาคอร์ต (เสี่ยงหาไม่ได้) หรือยืนยันคอร์ตก่อนแล้วค่อย
เปิดรับ (เสี่ยงจ่ายค่าคอร์ตแล้วทีมไม่มา)

LSN-0025 ให้ผู้จัดยืนยันคอร์ตเองได้แล้ว จึงมีทางที่สามคือให้เจ้าภาพกดยืนยัน
เมื่อไรก็ได้ แต่ต้องตัดสินว่าอันไหนกั้นอันไหน

### 3. เจ้าภาพนับเป็นหนึ่งทีมอัตโนมัติไหม และต้องจ่ายค่าสมัครตัวเองไหม

กระทบการนับ `min_teams` โดยตรง — ถ้าเจ้าภาพนับด้วย ขั้นต่ำ 4 ทีมแปลว่า
ชวนเพิ่มอีก 3 ซึ่งตรงกับ flow ต้นฉบับที่ผู้ใช้เขียนไว้ แต่ยังไม่เคยเขียนเป็นกติกา
