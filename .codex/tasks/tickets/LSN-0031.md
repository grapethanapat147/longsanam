# 🟢 LSN-0031 — คะแนนฝีมือจากผลแมตช์

**Type:** Feature · **Phase:** 10 · **Status:** Done
**Spec:** `.codex/specs/tournaments.md` — "เรื่องที่อันตรายที่สุด: คะแนนฝีมือ"
**Depends on:** LSN-0030 (ผลแมตช์ยืนยันสองฝั่ง) — merge แล้ว

## Goal

คำนวณ **คะแนนฝีมือจากผลแมตช์ที่ยืนยันแล้วเท่านั้น** แล้วแสดงให้เจ้าตัวและผู้จัดเห็น
พร้อมบอกชัดว่าคะแนนไหน **ยังไม่ผ่านสนามจริงพอ**

## ขอบเขตที่ตัดสินแล้ว: คิดและแสดง ยังไม่บังคับ

สเปกบอกว่าคะแนนนี้มีไว้ "กำหนดรุ่นที่ลงได้" แต่ตั๋วนี้ **ยังไม่เปิดด่านตอนสมัคร**

`join_tournament` วันนี้ไม่เช็ครุ่นเลย การเปิดด่านแปลว่าจู่ ๆ คนที่เคยสมัครได้จะ
สมัครไม่ได้ ซึ่งเป็นการเปลี่ยนพฤติกรรมที่ไม่ควรทำพร้อมกับการเปิดตัวสูตรที่ยังไม่มีใคร
เคยเห็นผลจริง **ให้คะแนนเดินก่อน ดูว่าสมเหตุสมผลไหม แล้วค่อยเปิดด่านในตั๋วแยก**

## Decisions

### 1. คะแนนมาจากผลแมตช์เท่านั้น — สเปกตัดสินไว้แล้ว

ให้คนประเมินกันเองแล้วเอามากำหนดรุ่น = ช่องโหว่สองทาง คือกดคะแนนตัวเองให้ต่ำ
เพื่อลงรุ่นอ่อน และดันคะแนนคู่แข่งให้สูงเพื่อผลักไปรุ่นที่สู้ไม่ไหว
ผลแมตช์โกงยากกว่า เพราะการทำให้คะแนนตัวเองต่ำแปลว่าต้อง **แพ้จริง**

### 2. Elo ปรับสำหรับคู่ ไม่คิดสเกลใหม่

- เริ่มที่ **1000** ทุกคน
- คะแนนของฝั่ง = **ค่าเฉลี่ยของผู้เล่นฝั่งนั้น** (แมตช์มีได้ 1–2 คนต่อฝั่ง)
- คาดหวัง `Ea = 1 / (1 + 10^((Rb − Ra)/400))` · ผู้เล่นทุกคนในฝั่งได้เดลต้าเท่ากัน
- **K = 40 ตอนยังไม่ยืนยัน · K = 20 หลังจากนั้น** ให้คนใหม่เข้าที่เร็ว
- `provisional = true` จนกว่าจะแข่งครบ **10 แมตช์ที่ยืนยันแล้ว**

Elo เป็นของที่วงการกีฬาใช้กันมานานและอธิบายได้ ไม่ต้องสอนตลาดใหม่

### 3. รุ่นมาจากคะแนน ใช้สเกล "มือ" ที่วงการแบดไทยใช้อยู่แล้ว

ไม่สร้างสเกลใหม่ — `tournament_tier` มี enum `N · S · P · C · B · A` อยู่แล้ว
เรียงจากอ่อนไปแข็ง เริ่มที่ 1000 จึงตกรุ่น **P** ซึ่งอยู่กลาง

| คะแนน | รุ่น |
| --- | --- |
| < 900 | N |
| 900–999 | S |
| 1000–1099 | P |
| 1100–1199 | C |
| 1200–1299 | B |
| ≥ 1300 | A |

### 4. คิดใหม่ทั้งชุดทุกครั้ง ไม่บวกทีละแมตช์

Elo แบบบวกสะสมขึ้นกับลำดับ และ **ย้อนกลับไม่ได้** ถ้ามีแมตช์ถูก `void`
แต่คอมเมนต์ใน `20260920000100_matches.sql` เขียนไว้เองแล้วว่า

> ผลคือชุดของแมตช์ที่ confirmed แค่เล็กลง LSN-0031 จึงคิดคะแนนใหม่จากชุดปัจจุบัน
> ได้เหมือนเดิม ไม่ต้องมีกลไกคิดย้อนหลัง

จึงทำเป็น `recompute_player_skill()` ที่สร้างตารางใหม่จาก `confirmed_matches`
ทั้งหมดเรียงตาม `played_at` แล้วเรียกมันท้าย `confirm_match` และ `void_match`
**เป็นฟังก์ชันภายใน ไม่ grant ให้ใครเรียกจากข้างนอก**

ข้อแลกเปลี่ยน: ต้นทุนเป็น O(จำนวนแมตช์ทั้งหมด) ต่อการยืนยันหนึ่งครั้ง ซึ่งรับได้
ที่ขนาดของ MVP และแลกมาด้วยความถูกต้องที่ไม่มีทางเพี้ยนสะสม

### 5. ห้ามยุ่งกับ `player_credit` เด็ดขาด

สเปกเขียนเป็น non-goal ตรง ๆ มือเก่งที่เบี้ยวเงินยังต้องถูกตัดสิทธิ์จ่ายทีหลัง
และมือใหม่ที่จ่ายตรงไม่ควรได้ลงรุ่นเกินตัว — ปักด้วยเทส

## Scope

- ตาราง `player_skill` ตามสเปก: `user_id · tier · rating · provisional · matches_played · updated_at`
- `recompute_player_skill()` และการเรียกจาก `confirm_match` / `void_match`
- RLS: อ่านได้โดย `authenticated` เพราะคะแนนฝีมือเป็นของสาธารณะในวงการอยู่แล้ว
  (ประกาศรับสมัครเขียน "รับมือ N–S" กันเปิดเผย) เขียนได้เฉพาะระบบ
- แสดงบนหน้าโปรไฟล์ พร้อมป้าย "ยังไม่ยืนยัน" เมื่อ `provisional`

## Non-goals

- **ไม่บังคับรุ่นตอนสมัคร** — ตั๋วแยก
- ไม่ทำการประเมินกันเองเรื่องมารยาท/ตรงเวลา — สเปกวางไว้เป็นแกนที่สอง แต่คนละงาน
- ไม่ใช้คะแนนเพื่อนร่วมก๊วนเป็นจุดตั้งต้นของคนใหม่ — รอจนมีแกนที่สองก่อน
  ระหว่างนี้คนใหม่เริ่มที่ 1000 และติดป้าย `provisional`
- ไม่เก็บค่าเฉลี่ยของก๊วนเป็นคอลัมน์ — สเปกสั่งห้าม เพราะจะเพี้ยนทันทีที่มีคนเข้าออก

### สองอย่างที่เจอระหว่างทำ

**1. seed ไม่ได้ผ่าน `confirm_match`** — seed ใส่แมตช์ตรงเข้าตาราง จึงไม่มีอะไรไป
สั่งคิดคะแนน ตารางว่างเปล่าทั้งที่มีแมตช์ที่ยืนยันแล้วอยู่ เติม
`select public.recompute_player_skill();` ท้าย seed

**2. `src/types/database.ts` เขียนมือ** — ไม่เติมตารางใหม่เข้าไป query จะ resolve
เป็น `SelectQueryError` แล้ว typecheck พัง เป็นกับดักเดียวกับที่โปรเจกต์ famai เจอ

### เรื่องที่เจอแล้วจัดการแบบตั้งใจ ไม่ใช่ปล่อยผ่าน

ตาราง `matches` ยอมให้ `score_a = score_b` ได้ ซึ่งเป็นผลที่เกิดไม่ได้ในแบดมินตันจริง
**ไม่แก้ในตั๋วนี้** เพราะเป็นเรื่องของ LSN-0030 และการเพิ่ม constraint ตอนนี้จะกระทบ
ข้อมูลที่มีอยู่ แต่สูตรต้องไม่พังถ้าเจอ จึงให้เสมอ = แบ่งครึ่ง (`v_sa = 0.5`)
แทนที่จะให้ฝั่งใดฝั่งหนึ่งได้ไปฟรี ๆ — เขียนคอมเมนต์ไว้ตรงจุดแล้ว

**ควรเปิดตั๋วแยกเพิ่ม constraint `score_a <> score_b` บน `matches`**
