# LSN-0011 — Automatic booking orchestration

**Type:** Feature · **Phase:** 4 · **Status:** Done

## Acceptance criteria
- [x] Triggered when paid headcount and paid total both clear the thresholds.
- [x] Re-checks availability server-side before every hold.
- [x] Creates an expiring hold, then requests/confirms the booking.
- [x] Walks approved fallbacks in priority order; never books an unapproved court.
- [x] All options exhausted -> `BookingFailed` + organizer notification with next actions.
- [x] Retry-safe via idempotency keys; every transition written to `audit_logs`.

## Review notes
- Verified end to end: the ReadyToBook session held and confirmed its
  first-priority court, wrote `session.holding_court → hold.created →
  booking.confirmed → session.booked` to the audit log, and notified all four
  paid participants.
- **Fallback safety verified explicitly.** With both approved courts blocked and
  the unapproved court free, the orchestrator marked the session
  `booking_failed` and left zero holds and zero bookings on the unapproved
  court.
- Concurrency verified: with one transaction holding a court, a second
  connection blocked for the full duration on the advisory lock and then
  correctly returned `slot_taken`. A direct overlapping INSERT is refused by the
  `bookings_no_overlap` exclusion constraint even as superuser.
