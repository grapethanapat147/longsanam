# LSN-0022 — Guests: sign a friend up without an account

**Type:** Feature · **Phase:** 8 · **Status:** Review
**Spec:** `.codex/specs/guest-participants.md`
**Depends on:** LSN-0019 (chase must skip guests), LSN-0020 (`mark_no_shows` already
filters `user_id is not null`), LSN-0021 (guests count in the settlement denominator)

## Goal
"พี่ต้น +1" is how every group fills its last seats, and Longsanam cannot
represent it: `session_participants.user_id` is `NOT NULL`. The organizer's only
options today are to make their friend install and sign up, or to leave them off
the list and take cash on the side — at which point the headcount, the receipt
and the booking threshold are all wrong.

For a product whose pitch is "open the link", "go make an account first" is the
wrong second step.

## Decisions already made
- **A guest is a participant with a name and no user.** `user_id` becomes
  nullable, `guest_name text` is added, and a check constraint requires exactly
  one of the two.
- **Only the organizer adds guests**, and says at that moment how the seat is
  paid: cash already taken, or pay later.
- **Guests are never chased and never credited.** There is no user to notify and
  no score to move. A guest's unpaid seat shows on the receipt as owing and the
  organizer settles it the way they always have. This is what keeps the credit
  system honest — a score must never move because of someone who cannot see it.
- **Claiming is deferred.** Linking a guest row to a real account when the
  friend eventually signs up is a follow-up ticket.

## Scope
- `session_participants.user_id` nullable, `guest_name text`, and a check
  constraint that exactly one is present.
- `add_guest_participant(p_session_id, p_guest_name, p_paid_cash boolean)` —
  organizer only, writes `audit_logs` including the organizer's attestation when
  cash is claimed.
- `remove_guest_participant(p_participant_id)` — organizer only, while the
  session is still open.
- Guard every path that assumes a user: `join_session`, `payForSlotAction`,
  `grant_pay_later`, `record_chase`, `list_chaseable_participants`,
  `set_check_in`, `settle_session_costs`.
- Organizer UI: add a guest by name with the two payment choices; the row shows
  a "ผู้เล่นรับเชิญ" chip.

## Non-goals
- Guest self-service of any kind.
- Claiming a guest row into a real account.
- Chasing, crediting or notifying a guest.
- Refunding a guest through the platform — their money never entered it.

## Acceptance criteria
- [x] Organizer can add a guest by name with either payment choice; the row
      appears with a "ผู้เล่นรับเชิญ" chip.
- [x] Organizer can remove a guest while the session is still open.
- [x] `list_chaseable_participants()` never returns a guest, pinned.
- [x] `mark_no_shows()` never charges a guest, pinned.
- [x] `join_session`, `payForSlotAction`, `grant_pay_later` and `record_chase`
      refuse a guest row with a clear reason.
- [x] A guest counts in LSN-0021's settlement denominator, pinned.
- [x] Every existing pgTAP assertion still passes with `user_id` nullable.

## Validation
- `npm run lint`, `npx tsc --noEmit`, `npm test` pass.
- `npm run test:db` passes, including the 35 assertions that exist today.
- Migration applies from scratch via `npm run db:reset`.
- No non-functional UI: the add-guest control either works or is disabled with
  its reason shown.

## Open questions — both decided at planning

- **A cash-paid guest counts toward `min_players`, and `payments.user_id`
  becomes nullable to make that true.** A guest gets a real payment row with
  provider `cash`, so `settle_payment()`'s "a paid seat has money behind it"
  join still holds. The alternative — loosening that join to a `left join` —
  would have been one line and would have given up the invariant LSN-0019 was
  built to protect.
- **Un-refundable guest cash is stated twice**, in the cancel dialog and on the
  receipt. A guest's money never entered the platform, so the organizer has to
  hand it back; they are told when they cancel and again when they read the
  receipt. The receipt half is handed to LSN-0023.

## Implementation plan

**Goal:** Let an organizer put "พี่ต้น +1" in the list without their friend
installing anything, and keep every rule the previous three tickets built
correct while a participant may have no account at all.

**Architecture:** Two phases, and the boundary between them matters. Phase one
(Tasks 1–5) widens the schema and hardens every function that assumed a user;
it ships nothing visible and its success condition is that **all 35 existing
pgTAP assertions still pass**. Phase two (Tasks 6–8) adds the organizer's
control and the two warnings. Doing it in that order means a regression in the
old rules shows up before any new surface exists to blame.

**Both open questions are decided, and the first one is why this ticket is the
largest of the four:**

1. **A cash-paid guest counts toward `min_players`, so `payments.user_id`
   becomes nullable** and a guest gets a real payment row with provider `cash`.
   This keeps the invariant LSN-0019 exists to protect — a seat that claims to
   be paid has money behind it — rather than loosening `settle_payment()`'s join
   to accept a seat with no payment at all. The cost is that the
   `payments_read` policy (`user_id = auth.uid() OR is_session_organizer(...)`)
   now has a null on the left of that comparison for guests. `null = uuid` is
   null, not false, so the row simply falls through to the organizer clause —
   which is the behaviour we want, and Task 4 pins it rather than trusting it.
2. **Un-refundable guest cash is stated twice**, in the cancel dialog and on the
   receipt. A guest's money never entered the platform, so `refundAllPaidParticipants`
   cannot return it; the organizer has to hand it back, and they should be told
   at the moment they cancel and again when they read the receipt.

**Tech stack:** Next.js 16 App Router, React 19, TypeScript strict, Supabase
Postgres + RLS, Vitest, pgTAP.

### Task 2 — Refuse a guest where an account is required

**Files:**
- Modify: `supabase/migrations/20260911000100_guest_participants.sql`

Nine SECURITY DEFINER functions read `user_id`. Most are safe because a guest
can never reach them — `join_session` starts from `auth.uid()`, `start_payment`

- [ ] **Step 1: Append the guards**

```sql
-- ---------------------------------------------------------------------------
-- Guards. A guest row is reachable from the organizer's own actions, so the
-- functions those actions call must say no rather than dereference a null.
-- ---------------------------------------------------------------------------

create or replace function public.grant_pay_later(p_participant_id uuid)
returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_p       public.session_participants%rowtype;
  v_session public.sessions%rowtype;
  v_payment public.payments%rowtype;
  v_score   integer;
begin
  select * into v_p from public.session_participants where id = p_participant_id for update;
  if v_p.id is null then
    return jsonb_build_object('ok', false, 'reason', 'not_found');
  end if;

  -- A guest has no credit to stake, so there is nothing for pay-later to gate.
  -- The organizer already chose how a guest's seat is paid when they added it.
  if v_p.user_id is null then
    return jsonb_build_object('ok', false, 'reason', 'guest_has_no_account');
  end if;

  select * into v_session from public.sessions where id = v_p.session_id;

  if not public.is_session_organizer(v_session.id) then
    return jsonb_build_object('ok', false, 'reason', 'not_organizer');
  end if;

  if v_session.status in ('completed', 'cancelled') then
    return jsonb_build_object('ok', false, 'reason', 'session_closed');
  end if;

  if v_p.status <> 'joined_pending_payment' then
    return jsonb_build_object('ok', false, 'reason', 'wrong_state');
  end if;

  select score into v_score from public.player_credit where user_id = v_p.user_id;
  if coalesce(v_score, 100) < 70 then
    return jsonb_build_object('ok', false, 'reason', 'credit_too_low',
      'score', coalesce(v_score, 100));
  end if;

  update public.session_participants
  set status = 'joined_pay_later',
      pay_later_granted_at = now(),
      pay_later_granted_by = auth.uid()
  where id = p_participant_id;

  select * into v_payment
  from public.payments
  where participant_id = p_participant_id and status in ('pending', 'paid')
  limit 1;

  if v_payment.id is null then
    insert into public.payments
      (session_id, participant_id, user_id, amount_thb, status, idempotency_key, expires_at)
    values
      (v_p.session_id, p_participant_id, v_p.user_id, v_p.amount_due_thb, 'pending',
       'paylater:' || p_participant_id::text, null);
  elsif v_payment.status = 'pending' then
    update public.payments set expires_at = null where id = v_payment.id;
  end if;

  perform public.app_log(auth.uid(), 'session_participant', p_participant_id, v_p.session_id,
    'participant.pay_later_granted', 'joined_pending_payment', 'joined_pay_later',
    jsonb_build_object('amountThb', v_p.amount_due_thb));

  return jsonb_build_object('ok', true);
end;
$$;

create or replace function public.record_chase(
  p_participant_id uuid,
  p_delta          integer,
  p_reason         text,
  p_title          text,
  p_body           text
) returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_p   public.session_participants%rowtype;
  v_new integer;
begin
  select * into v_p from public.session_participants where id = p_participant_id for update;
  if v_p.id is null then
    return jsonb_build_object('ok', false, 'reason', 'not_found');
  end if;

  -- Nobody to notify and no score to move. list_chaseable_participants already
  -- filters guests out; this is the second guard, because a wrong charge lands
  -- on a real person's record.
  if v_p.user_id is null then
    return jsonb_build_object('ok', false, 'reason', 'guest_has_no_account');
  end if;

  if v_p.status = 'joined_pay_later' then
    update public.session_participants set status = 'payment_overdue' where id = p_participant_id;
    perform public.app_log(null, 'session_participant', p_participant_id, v_p.session_id,
      'participant.payment_overdue', 'joined_pay_later', 'payment_overdue', '{}'::jsonb);
  end if;

  update public.session_participants set last_chased_at = now() where id = p_participant_id;

  if p_delta <> 0 then
    insert into public.player_credit (user_id, score) values (v_p.user_id, 100)
    on conflict (user_id) do nothing;

    update public.player_credit
    set score = greatest(0, least(100, score + p_delta))
    where user_id = v_p.user_id
    returning score into v_new;

    insert into public.credit_events (user_id, session_id, delta, reason)
    values (v_p.user_id, v_p.session_id, p_delta, p_reason);

    perform public.app_log(null, 'player_credit', v_p.user_id, v_p.session_id,
      'credit.charged', null, v_new::text, jsonb_build_object('delta', p_delta));
  end if;

  perform public.notify_user(v_p.user_id, v_p.session_id, 'payment_overdue',
    p_title, p_body, null);

  return jsonb_build_object('ok', true, 'score', v_new);
end;
$$;

-- The chase listing already joins profile_contacts on sp.user_id, which yields
-- nothing for a guest — but "yields nothing" is a left join returning a row
-- with a null contact, not a row that is absent. Filter explicitly.
drop function if exists public.list_chaseable_participants();

create function public.list_chaseable_participants()
returns table (
  participant_id uuid,
  user_id        uuid,
  session_id     uuid,
  session_title  text,
  amount_due_thb integer,
  ends_at        timestamptz,
  last_chased_at timestamptz,
  status         public.participant_status,
  line_user_id   text,
  checked_in_at  timestamptz
)
language sql
security definer
set search_path = public, pg_temp
as $$
  select sp.id, sp.user_id, sp.session_id, s.title, sp.amount_due_thb,
         s.ends_at, sp.last_chased_at, sp.status, pc.line_user_id, sp.checked_in_at
  from public.session_participants sp
  join public.sessions s on s.id = sp.session_id
  left join public.profile_contacts pc on pc.user_id = sp.user_id
  where sp.status in ('joined_pay_later', 'payment_overdue')
    and sp.user_id is not null
    and s.ends_at + interval '2 hours' <= now()
    and s.ends_at + interval '14 days' > now();
$$;

revoke execute on function public.list_chaseable_participants() from public, authenticated;
grant execute on function public.list_chaseable_participants() to service_role;
```

### Task 3 — Adding and removing a guest

**Files:**
- Modify: `supabase/migrations/20260911000100_guest_participants.sql`

- [ ] **Step 1: Append the two RPCs**

```sql
-- ---------------------------------------------------------------------------
-- The organizer vouches for a guest.
--
-- Cash-paid means the organizer says they have the money. That is a trust
-- extension, and a deliberate one: it is their session, their money, and their
-- word is already what the venue relies on. The attestation is logged with
-- their id so the claim has an author.
-- ---------------------------------------------------------------------------

create or replace function public.add_guest_participant(
  p_session_id uuid,
  p_guest_name text,
  p_paid_cash  boolean
) returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_session public.sessions%rowtype;
  v_taken   integer;
  v_id      uuid;
  v_amount  integer;
begin
  select * into v_session from public.sessions where id = p_session_id for update;
  if v_session.id is null then
    return jsonb_build_object('ok', false, 'reason', 'session_not_found');
  end if;

  if not public.is_session_organizer(p_session_id) then
    return jsonb_build_object('ok', false, 'reason', 'not_organizer');
  end if;

  if v_session.status not in ('open', 'ready_to_book', 'holding_court', 'booked') then
    return jsonb_build_object('ok', false, 'reason', 'session_not_open');
  end if;

  if p_guest_name is null or length(btrim(p_guest_name)) = 0 then
    return jsonb_build_object('ok', false, 'reason', 'guest_name_required');
  end if;

  select count(*) into v_taken
  from public.session_participants
  where session_id = p_session_id
    and status in ('joined_pending_payment', 'paid_confirmed',
                   'joined_pay_later', 'payment_overdue');

  if v_taken >= v_session.target_players then
    return jsonb_build_object('ok', false, 'reason', 'session_full');
  end if;

  v_amount := coalesce(v_session.settled_per_person_thb, v_session.budget_per_person_thb);

  insert into public.session_participants
    (session_id, user_id, guest_name, added_by_organizer, status,
     amount_due_thb, payment_due_at)
  values
    (p_session_id, null, btrim(p_guest_name), auth.uid(),
     case when p_paid_cash then 'paid_confirmed'::public.participant_status
          else 'joined_pay_later'::public.participant_status end,
     v_amount, v_session.payment_deadline)
  returning id into v_id;

  -- Both paths get a real payment row. A paid seat has money behind it; an
  -- unpaid one has a debt with no deadline, exactly like a granted pay-later.
  insert into public.payments
    (session_id, participant_id, user_id, amount_thb, status, provider,
     idempotency_key, expires_at, paid_at)
  values
    (p_session_id, v_id, null, v_amount,
     case when p_paid_cash then 'paid'::public.payment_status
          else 'pending'::public.payment_status end,
     'cash', 'guest:' || v_id::text, null,
     case when p_paid_cash then now() else null end);

  perform public.app_log(auth.uid(), 'session_participant', v_id, p_session_id,
    'participant.guest_added', null,
    case when p_paid_cash then 'paid_confirmed' else 'joined_pay_later' end,
    jsonb_build_object('guestName', btrim(p_guest_name), 'paidCash', p_paid_cash,
      'amountThb', v_amount, 'attestedBy', auth.uid()));

  return jsonb_build_object('ok', true, 'participantId', v_id, 'amountThb', v_amount);
end;
$$;

create or replace function public.remove_guest_participant(p_participant_id uuid)
returns jsonb
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_p       public.session_participants%rowtype;
  v_session public.sessions%rowtype;
begin
  select * into v_p from public.session_participants where id = p_participant_id for update;
  if v_p.id is null then
    return jsonb_build_object('ok', false, 'reason', 'not_found');
  end if;

  if v_p.user_id is not null then
    return jsonb_build_object('ok', false, 'reason', 'not_a_guest');
  end if;

  if not public.is_session_organizer(v_p.session_id) then
    return jsonb_build_object('ok', false, 'reason', 'not_organizer');
  end if;

  select * into v_session from public.sessions where id = v_p.session_id;
  if v_session.status in ('completed', 'cancelled', 'booking_failed') then
    return jsonb_build_object('ok', false, 'reason', 'session_closed');
  end if;

  update public.payments set status = 'expired'
  where participant_id = p_participant_id and status = 'pending';

  update public.session_participants
  set status = 'cancelled', cancelled_at = now()
  where id = p_participant_id;

  perform public.app_log(auth.uid(), 'session_participant', p_participant_id, v_p.session_id,
    'participant.guest_removed', v_p.status::text, 'cancelled',
    jsonb_build_object('guestName', v_p.guest_name));

  return jsonb_build_object('ok', true);
end;
$$;

revoke execute on function public.add_guest_participant(uuid, text, boolean) from public;
revoke execute on function public.remove_guest_participant(uuid) from public;
grant execute on function public.add_guest_participant(uuid, text, boolean) to authenticated;
grant execute on function public.remove_guest_participant(uuid) to authenticated;
```

### Task 4 — Prove the RLS null comparison behaves

**Files:**
- Create: `supabase/tests/guest_participants.test.sql`

`payments_read` is `user_id = auth.uid() OR is_session_organizer(session_id) OR
is_platform_admin()`. For a guest row `user_id` is null, so the first clause is
null rather than false — SQL three-valued logic then falls through to the
organizer clause. That is the behaviour we want and it is not obvious, so it
gets an assertion before anything is built on top of it.

- [ ] **Step 1: Write the tests**

```sql
-- Guests (LSN-0022). Run with `npm run test:db`.
--
-- Actors, from supabase/seed.sql:
--   organizer  1111…0001  organizes OPEN001
--   แนน        1111…0002  a player in OPEN001, not the organizer

begin;
select plan(11);

create or replace function pg_temp.act_as(p_id uuid) returns void
language plpgsql as $$
begin
  perform set_config('request.jwt.claims',
    json_build_object('sub', p_id, 'role', 'authenticated')::text, true);

$$;
```

```ts
  const { data, error } = await supabase.rpc('add_guest_participant', {

  });

  revalidatePath('/organizer', 'layout');
  revalidatePath('/s', 'layout');

}
```

### Risks and decisions

- **`null = auth.uid()` is null, not false.** The whole guest read path leans on
  SQL three-valued logic doing the safe thing in `payments_read`. Task 4 pins
  it. If a later ticket rewrites that policy with `coalesce(user_id, ...)` or
  `is not distinct from`, the behaviour changes silently.
- **`payForSlotAction` and `join_session` need no change, and that was
  checked rather than assumed.** `join_session` starts from `auth.uid()` so it
  cannot produce a guest. `payForSlotAction` compares
  `participant.user_id !== user.id`; for a guest the left side is null, so the
  comparison is true and the action refuses. Both are correct by accident, so
  the guest test pins the second one.
- **`unique (session_id, user_id)` already tolerates guests.** Postgres treats
  nulls as distinct in a unique index, so two guests in one session do not
  collide — verified against the live index, not assumed. Two guests may share a
  name, which is right: a guest is identified by the organizer, not by us.
- **Nine functions read `user_id`; three got explicit guards.** The other six
  are unreachable for a guest because they start from `auth.uid()` or from a
  seat the caller owns. That reasoning is worth re-checking during review — it
  is the kind of "cannot happen" that stops being true when a new caller appears.
- **A cash guest is an organizer's assertion, not a receipt.** Nothing verifies
  the money exists. The audit log records who claimed it, which is the most the
  system can honestly offer.
- **`add_guest_participant` uses `settled_per_person_thb` when it exists**, so a
  guest added after LSN-0021's settlement owes the settled figure rather than
  the original guess.
