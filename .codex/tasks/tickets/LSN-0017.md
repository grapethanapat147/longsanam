# LSN-0017 — Image uploads (Supabase Storage)

**Type:** Feature · **Phase:** 7 · **Status:** Done

## Goal
Venues and players can have a picture. `venues.cover_image_url` and
`profiles.avatar_url` already exist but nothing writes to them.

## Acceptance criteria
- [x] `venue-images` and `avatars` buckets, public read, created by migration.
- [x] Storage RLS: a user writes only into their own avatar folder; a venue
      member writes only into their venue's folder.
- [x] Server actions validate MIME type and size before upload.
- [x] Venue admin can upload/replace a cover image.
- [x] Player can upload/replace an avatar.
- [x] Images render on the venue portal, the discover cards and the session page.
- [x] Replacing an image removes the previous object rather than orphaning it.

## Review notes
- Storage policies verified with real access tokens rather than by reading the
  SQL: uploading to one's own avatar folder and to an owned venue succeeded;
  another user's avatar folder, a foreign venue, a non-UUID folder and an
  anonymous upload were all refused. Public read of an uploaded object returns
  200 without a token, which is what a link shared into LINE needs.
- `next/image` needed two fixes that only show up locally:
  `next.config` is evaluated before Next loads `.env`, so the storage host has
  to be read through `@next/env` or `remotePatterns` is empty; and Next 16
  refuses upstream images resolving to a private IP. That SSRF default is
  correct, so the exception is granted only when the configured Supabase host
  is this machine — never for a deployed environment.
- A failed `profiles`/`venues` update removes the object it just uploaded, so a
  stored file never outlives the row that was supposed to point at it.
