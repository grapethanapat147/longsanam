# 🟢 LSN-0023 — ใบสรุปก๊วน ที่ส่งกลับเข้า LINE ได้

**Type:** Feature · **Phase:** 9 · **Status:** Review
**Spec:** `.codex/specs/session-receipt.md`
**Depends on:** LSN-0020 (ใครมาจริง), LSN-0021 (ยอดต่อหัวที่สรุปแล้ว), LSN-0022 (ผู้เล่นรับเชิญ) — **ทั้งสามใบ merge แล้ว**

## Goal

หน้า `/s/[code]/receipt` ที่สรุปว่าใครมา ค่าใช้จ่ายเท่าไร ใครจ่ายแล้ว ใครยังค้าง
แล้วส่งกลับเข้ากลุ่ม LINE ได้ พร้อมภาพ preview ที่ LINE เรนเดอร์ให้

ทุกวันนี้ผู้จัดพิมพ์ข้อความนี้เองทุกครั้งหลังเล่นจบ ซึ่งเป็น core loop ของโปรดักต์
ที่ถูกเขียนด้วยมือ — และข้อมูลทุกบรรทัดที่ต้องใช้ระบบมีอยู่แล้ว

## Context

สามใบก่อนหน้าสร้างข้อมูลไว้ครบแล้ว ตั๋วนี้แค่เอามาแสดง:

| บรรทัด | แหล่ง | fallback |
| --- | --- | --- |
| ใครเล่น | `checked_in_at` (LSN-0020) | สถานะ paid / pay-later |
| ต่อหัว | `settled_per_person_thb` (LSN-0021) | `budget_per_person_thb` |
| ผู้เล่นรับเชิญ | `guest_name` (LSN-0022) | — |
| จ่ายแล้ว / ค้าง | `payments.status` | — |

ตรวจแล้วว่าคอลัมน์ทั้งสี่มีอยู่จริงบน `main` และ `lineShareUrl` ที่จะใช้ปุ่มแชร์
มีอยู่แล้วที่ `src/lib/line/share.ts`

## Scope

- route ใหม่ `src/app/s/[code]/receipt/page.tsx`
- สองมุมมองบนหน้าเดียวกัน: ผู้เล่นและผู้จัดเห็นชื่อ · คนนอกเห็นแต่ยอดรวมกับจำนวนคน
- `og:image` ที่สร้างด้วย Next.js `ImageResponse` ในภาษาภาพของระบบ
- ปุ่ม "ส่งใบเสร็จเข้า LINE" ใช้ `lineShareUrl` ที่มีอยู่แล้ว
- คำเตือนเรื่องเงินสดผู้เล่นรับเชิญคืนผ่านระบบไม่ได้ — **ส่งต่อมาจาก LSN-0022**
  ตอนนี้ขึ้นแค่ในกล่องยกเลิกก๊วน ต้องขึ้นบนใบสรุปด้วย

## Non-goals

- ไม่ทำ PDF export
- ไม่แสดงรายละเอียดรายเกม
- ไม่มีปุ่มจ่ายเงินบนใบสรุป — ปุ่มจ่ายอยู่ที่หน้าก๊วนซึ่งเป็นที่ที่ flow การจ่ายอยู่

## เรื่องที่ spec เขียนไว้แต่ทำแบบนั้นไม่ได้ — ตัดสินแล้ว

spec เขียนว่า *"Non-participants see masked names and correct totals; participants
and the organizer see names. **RLS-level**, pinned by pgTAP"*

**การปิดชื่อแบบนี้ไม่ใช่สิ่งที่ RLS ทำได้** RLS ทำงานระดับแถว ไม่ใช่ระดับคอลัมน์
มันตอบได้แค่ "เห็นแถวนี้" กับ "ไม่เห็นแถวนี้" ไม่ใช่ "เห็นแถวนี้แต่ชื่อถูกปิด"

ไล่ดูของจริงบนฐานข้อมูลแล้วได้ภาพนี้:

| | ผลจริง |
| --- | --- |
| `participants_read` policy | `for select to authenticated` — **anon ไม่อยู่ในนั้นเลย** |
| `has_table_privilege('anon', 'session_participants', 'select')` | `false` |
| `has_function_privilege('anon', 'session_progress(uuid)', 'execute')` | `true` |
| anon เรียก `session_progress()` จริง | `ERROR: permission denied for table session_participants` |

ตัวสุดท้ายคือจุดสำคัญ: `session_progress()` **ถูก grant ให้ anon จริง** แต่มันเป็น
SECURITY INVOKER ไม่ใช่ DEFINER พอ anon เรียก มันก็ไปอ่าน `session_participants`
ด้วยสิทธิ์ของ anon แล้วตาย ทุกวันนี้หน้า `/s/[code]` ใช้ได้เพราะเรียกผ่าน
`createAdminClient()` ฝั่ง server ซึ่ง bypass RLS

**สองทางที่พิจารณา:**

| ทาง | ทำอะไร | ได้อะไร | เสียอะไร |
| --- | --- | --- | --- |
| **A. RPC รวมยอด SECURITY DEFINER** | เขียนฟังก์ชันใหม่ที่คืนเฉพาะตัวเลข (จำนวนคน จ่ายแล้ว ค้าง ยอดรวม) ไม่มีชื่อ ไม่มีแถว grant ให้ anon | ฐานข้อมูลเป็นคนบังคับ ไม่มีชื่อหลุดแม้โค้ดหน้าเพี้ยน · pgTAP ปักได้ตรงตามที่ spec ตั้งใจ | มีฟังก์ชันเพิ่มอีกตัว และต้องระวัง `search_path` แบบ DEFINER ตัวอื่น |
| **B. ปิดชื่อฝั่ง server component** | อ่านด้วย `createAdminClient()` แล้วตัดชื่อออกก่อนส่งลง HTML ตามสถานะผู้ใช้ | ไม่ต้องเพิ่มฟังก์ชัน เหมือนที่ `/s/[code]` ทำอยู่แล้ว | การปิดชื่ออยู่ในโค้ดหน้า ถ้าลืม branch เดียวชื่อหลุดทันที และ pgTAP ปักไม่ได้ ต้องใช้เทสคนละชนิด |

**เลือกทาง A** (เกรพยืนยัน 11 ก.ย.) เพราะหน้านี้ถูกออกแบบมาให้คนแปลกหน้าเปิดจาก
แชท LINE ซึ่งแปลว่าเส้นทาง "คนนอกเห็นหน้านี้" คือเส้นทางหลัก ไม่ใช่ edge case
และเพราะ spec สั่งให้ pin ด้วย pgTAP ซึ่งทำได้จริงเฉพาะทาง A

**สิ่งที่ทาง A ต้องมี:**

- RPC ใหม่ `session_receipt_public(uuid)` — `security definer` · `set search_path
  = public, pg_temp` ตามแบบเดียวกับ DEFINER ตัวอื่นในโปรเจกต์
- คืนเฉพาะตัวเลข: จำนวนผู้เล่น · จ่ายแล้วกี่คน · ค้างกี่คน · ยอดต่อหัว · ยอดรวม
  **ไม่มีชื่อ ไม่มี id ของผู้เล่น ไม่มีแถวรายคน** — สิ่งที่ไม่ได้คืน คือสิ่งที่หลุดไม่ได้
- **grant ด้วย `revoke ... from public` แล้ว `grant ... to anon, authenticated`
  ในไฟล์ migration ใหม่เอง** ไม่ใช่เพิ่มชื่อเข้า array `v_public`
  (ข้อนี้แก้จากที่เขียนไว้ตอนแรก ซึ่งผิด) — บล็อกที่ถือ `v_public` เป็น `do $$ ... $$`
  ที่รันครั้งเดียวตอน `20260901000300_rls.sql` apply ฟังก์ชันที่สร้างในไฟล์หลังจากนั้น
  ไม่ถูกแตะเลย การเพิ่มชื่อเข้า array จึงเป็น no-op
  และ**บรรทัด `revoke` ห้ามลืม** เพราะ Postgres ให้ `EXECUTE` กับ `PUBLIC`
  เป็นค่าเริ่มต้น — พิสูจน์แล้วว่า `anon` เรียกฟังก์ชันที่เพิ่งสร้างได้ทันที
  นี่คือรูปแบบที่ `settle_session_costs` และ `add_guest_participant` ใช้อยู่
- ฝั่งที่เห็นชื่อ (ผู้เล่น/ผู้จัด) ใช้เส้นทางเดิมผ่าน `createAdminClient()` ฝั่ง server
  เหมือนที่ `/s/[code]` ทำอยู่

## Decisions — ตัดสินครบแล้ว

### 1. การปิดชื่อ → ทาง A (RPC รวมยอดแบบ SECURITY DEFINER)

เกรพเลือก รายละเอียดอยู่ในหัวข้อด้านบน

### 2. ก๊วนสถานะไหนมีใบสรุปได้ → `completed` เท่านั้น

ใช้ **allowlist ไม่ใช่ denylist** ตามบทเรียนจาก LSN-0020

เหตุผล ไล่จากของจริง:

- ก๊วนกลายเป็น `completed` **โดยอัตโนมัติ** — `lifecycle` sweep ทำงานทุก 5 นาที
  แล้วเปลี่ยน `booked` → `completed` เมื่อ `ends_at <= now()` ผู้จัดไม่ต้องกดอะไร
  ใบสรุปจึงโผล่เองภายในไม่กี่นาทีหลังเล่นจบ ไม่มีเหตุผลต้องเปิดให้สถานะอื่น
- **ไม่เอา `booked`** แม้ `settle_session_costs()` จะยอมให้ settle ก๊วนที่ยัง `booked`
  ได้ก็ตาม (มันปฏิเสธแค่ `cancelled` กับ `booking_failed`) เพราะก๊วนที่ยังไม่เล่น
  ไม่มีใครเช็คอิน ยอดต่อหัวยังเป็นตัวประมาณ การเอาตัวประมาณไปแปะบนเอกสารชื่อ
  "ใบเสร็จ" คือความสับสนแบบเดียวกับที่ LSN-0021 มีไว้กำจัด
- **ไม่เอา `cancelled` / `booking_failed`** เพราะ trigger
  `void_pay_later_on_session_end()` **ล้าง `settled_per_person_thb` ทิ้ง** ตอนยกเลิก
  ใบสรุปของก๊วนที่ยกเลิกจึงไม่มียอดค่าใช้จ่ายให้แสดงเลย สิ่งที่ก๊วนยกเลิกต้องการคือ
  **สรุปการคืนเงิน** ซึ่งเป็นเอกสารคนละใบ มีบรรทัดคนละชุด — ยัดสองอย่างลงหน้าเดียว
  ทำให้แย่ทั้งคู่ บันทึกไว้เป็นตั๋วในอนาคตถ้าผู้ใช้ขอ

### 3. ยอดรวมนับรายการเก็บเงินเพิ่มไหม → เผื่อที่ไว้ แต่ยังไม่แสดงใน v1

ฟังก์ชันโหลดข้อมูลของใบสรุปคืน `charges: []` ตั้งแต่วันแรก และหน้าเรนเดอร์หัวข้อ
"ค่าใช้จ่ายเพิ่มเติม" เฉพาะเมื่อ array ไม่ว่าง

**นี่ไม่ใช่การเผื่ออนาคตแบบเดา** เพราะ LSN-0024 เขียน spec เสร็จแล้วและอยู่ใน
backlog เดียวกัน phase เดียวกัน และ spec ของมันกำหนดไว้แล้วว่ารายการเพิ่มเติมเป็น
**หนี้คนละก้อน** ที่ไม่แตะ `amount_due_thb` ดังนั้นใบสรุปต้องแสดงเป็นหัวข้อแยก
อยู่ดีไม่ว่าจะทำตั๋วไหนก่อน การใส่ array ว่างไว้ตั้งแต่แรกจึงแทบไม่มีต้นทุน
แต่ประหยัดการรื้อโครงทีหลัง

**ทางเลือกที่ไม่ได้เลือก:** ทำ LSN-0024 ก่อนแล้วค่อยทำใบสรุปทีเดียวจบ
ซึ่งสะอาดกว่าในแง่โค้ด แต่ใบสรุปคือฟีเจอร์ที่ดึงคนใหม่เข้ามาผ่าน LINE และมันมีค่า
ในตัวเองโดยไม่ต้องรอรายการเพิ่มเติม จึงไม่ควรถูกบล็อกไว้ — ถ้าเกรพอยากสลับลำดับ
เปลี่ยนได้ ไม่มีอะไรผูกไว้

```sql
-- ใบสรุปก๊วน (LSN-0023) — ยอดรวมสำหรับคนที่ไม่ได้อยู่ในก๊วน
--
-- RLS ทำงานระดับแถว ไม่ใช่ระดับคอลัมน์ มันคืน "เห็นแถว" หรือ "ไม่เห็นแถว"
-- ไม่ใช่ "เห็นแถวแต่ชื่อถูกปิด" การปิดชื่อจึงทำด้วยการ *ไม่คืนชื่อออกมาเลย*
-- สิ่งที่ไม่ได้คืน คือสิ่งที่หลุดไม่ได้
--
-- ตัวหารใช้กติกาเดียวกับ settle_session_costs() ของ LSN-0021 เป๊ะ ๆ:
-- ถ้ามีใครเช็คอินเลย นับเฉพาะคนที่เช็คอิน ถ้าไม่มีใครเช็คอินเลยนับทุกคนที่ถือที่นั่ง
-- ถ้าสองที่นี้ไม่ตรงกัน ใบสรุปจะบอกยอดคนละอย่างกับที่ระบบเรียกเก็บจริง

create or replace function public.session_receipt_public(p_session_id uuid)
returns jsonb
language plpgsql
security definer
stable
set search_path = public, pg_temp
as $$
declare
  v_session     public.sessions%rowtype;
  v_any_checkin boolean;
  v_players     integer;
  v_paid        integer;
  v_owing       integer;
  v_total       integer;
begin
  select * into v_session from public.sessions where id = p_session_id;

  -- allowlist ไม่ใช่ denylist ด้วยเหตุผลเดียวกับ mark_no_shows():
  -- denylist ปล่อย draft / open / ready_to_book / holding_court หลุดเข้ามา
  -- ซึ่งเป็นก๊วนที่ยังไม่เกิดขึ้น และ booked คือก๊วนที่ยังไม่เล่น
  if v_session.id is null or v_session.status <> 'completed' then
    return null;
  end if;

  select exists (
    select 1 from public.session_participants x
    where x.session_id = p_session_id and x.checked_in_at is not null
  ) into v_any_checkin;

  select count(*),
         count(*) filter (where sp.status = 'paid_confirmed'),
         count(*) filter (where sp.status in ('joined_pay_later', 'payment_overdue')),
         coalesce(sum(sp.amount_due_thb), 0)
    into v_players, v_paid, v_owing, v_total
  from public.session_participants sp
  where sp.session_id = p_session_id
    and sp.status in ('paid_confirmed', 'joined_pay_later', 'payment_overdue')
    and (not v_any_checkin or sp.checked_in_at is not null);

  return jsonb_build_object(
    'players',    v_players,
    'paid',       v_paid,
    'owing',      v_owing,
    'perHeadThb', coalesce(v_session.settled_per_person_thb, v_session.budget_per_person_thb),
    'totalThb',   v_total,
    'title',      v_session.title,
    'startsAt',   v_session.starts_at
  );
end;
$$;

-- Postgres ให้ EXECUTE กับ PUBLIC เป็นค่าเริ่มต้น บรรทัด revoke จึงห้ามลืม
-- แม้ผลลัพธ์สุดท้ายคือ anon เรียกได้อยู่ดี — เพื่อให้สิทธิ์ถูกเขียนไว้ชัด ไม่ใช่ตกทอดมา
revoke execute on function public.session_receipt_public(uuid) from public;
grant execute on function public.session_receipt_public(uuid)
  to anon, authenticated, service_role;
```

```ts
/**
 * ใบสรุปก๊วน (LSN-0023) — คืนสองมุมมองจากคำเรียกเดียว
 *
 * `viewer` ตัดสินว่าใครได้เห็นอะไร ไม่ใช่หน้าเว็บตัดสิน เพราะถ้าหน้าเว็บลืม branch
 * เดียวชื่อก็หลุด ฝั่งคนนอกจึงไม่เคยมี `names` ให้ลืมปิดตั้งแต่แรก
 */
export type ReceiptCharge = { id: string; label: string; amountThb: number };

export type ReceiptTotals = {
  players: number;
  paid: number;
  owing: number;
  perHeadThb: number;
  totalThb: number;
};

export type ReceiptName = {
  participantId: string;
  displayName: string;
  isGuest: boolean;
  paid: boolean;
  amountThb: number;
  paidCash: boolean;
};

export async function loadSessionReceipt(code: string, viewerId: string | null) {
  const supabase = await createClient();
  const { data: row } = await supabase
    .from('sessions')
    .select('id, public_code, title, starts_at, ends_at, status, organizer_id')
    .eq('public_code', code.toUpperCase())
    .maybeSingle();
  if (!row) return null;

  const session = row as {
    id: string; public_code: string; title: string;
    starts_at: string; ends_at: string; status: string; organizer_id: string;
  };
  if (session.status !== 'completed') return null;

  const admin = createAdminClient();
  const { data: totalsRaw } = await admin.rpc('session_receipt_public', {
    p_session_id: session.id,
  });
  if (!totalsRaw) return null;
  const totals = totalsRaw as unknown as ReceiptTotals;

  // LSN-0024 จะเติม session_charges เข้ามาตรงนี้ หน้าเรนเดอร์หัวข้อเฉพาะเมื่อไม่ว่าง
  const charges: ReceiptCharge[] = [];

  const isOrganizer = viewerId === session.organizer_id;
  let isParticipant = false;
  if (viewerId && !isOrganizer) {
    const { count } = await admin
      .from('session_participants')
      .select('id', { count: 'exact', head: true })
      .eq('session_id', session.id)
      .eq('user_id', viewerId);
    isParticipant = (count ?? 0) > 0;
  }

  if (!isOrganizer && !isParticipant) {
    return { session, totals, charges, names: null as ReceiptName[] | null };
  }

  const { data: rows } = await admin
    .from('session_participants')
    .select(
      'id, status, amount_due_thb, guest_name, ' +
        'profiles!session_participants_user_id_fkey (display_name), ' +
        'payments (status, provider)',
    )
    .eq('session_id', session.id)
    .in('status', ['paid_confirmed', 'joined_pay_later', 'payment_overdue']);

  const names: ReceiptName[] = (rows ?? []).map((r) => {
    const p = r as unknown as {
      id: string; status: string; amount_due_thb: number; guest_name: string | null;
      profiles: { display_name: string } | null;
      payments: { status: string; provider: string }[] | null;
    };
    const cashPaid = (p.payments ?? []).some(
      (x) => x.status === 'paid' && x.provider === 'cash',
    );
    return {
      participantId: p.id,
      displayName: p.guest_name ?? p.profiles?.display_name ?? 'ผู้เล่น',
      isGuest: p.guest_name !== null,
      paid: p.status === 'paid_confirmed',
      amountThb: p.amount_due_thb,
      paidCash: cashPaid,
    };
  });

  return { session, totals, charges, names };
}
```
