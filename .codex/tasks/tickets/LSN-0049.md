# 🔴 LSN-0049 — สิทธิ์ของฟังก์ชันบน production ไม่ตรงกับในเครื่อง

**Type:** Bugfix · **Phase:** 11 · **Status:** Done
**Source:** เจอตอนตรวจดัมป์สคีมาหลัง deploy LSN-0046

## อาการ

`complete_finished_tournaments()` ที่เพิ่ง deploy ไป เขียนไว้ว่าเป็นของเครื่อง

```sql
revoke execute on function public.complete_finished_tournaments() from public;
grant  execute on function public.complete_finished_tournaments() to service_role;
```

แต่ดัมป์สคีมาจาก production กลับบอกว่า

```
GRANT ALL ON FUNCTION "public"."complete_finished_tournaments"() TO "anon";
GRANT ALL ON FUNCTION "public"."complete_finished_tournaments"() TO "authenticated";
```

ไล่ดูทั้งชุดแล้วพบว่ามี **แปดฟังก์ชัน** ที่ปิดอยู่ในเครื่องแต่เปิดบน production:
`close_unfilled_tournaments` · `complete_finished_tournaments` ·
`list_chaseable_participants` · `mark_no_shows` · `recompute_player_skill` ·
`record_chase` · `session_denominator` · `tournament_groups_of`

## ต้นตอ

`20260901000300_rls.sql` ปิดประตูด้วยลูปที่ revoke ทุกฟังก์ชันใน `public`
แล้ว grant คืนเฉพาะรายชื่อใน `v_public` — **แต่ลูปนั้นวนกับฟังก์ชันที่มีอยู่ ณ วันนั้น**
ฟังก์ชันที่สร้างหลัง 1 ก.ย. ไม่เคยผ่านประตูบานนั้นเลย

สองอย่างทำให้มันเปิดบน production:
1. PostgreSQL ให้ `PUBLIC` มี EXECUTE เป็นค่าเริ่มต้นของฟังก์ชันใหม่
2. Supabase cloud มี `ALTER DEFAULT PRIVILEGES` แจก EXECUTE ให้ `anon`/`authenticated` ซ้ำอีกชั้น

`revoke ... from public` ที่เขียนไว้ **ไม่ลบสิทธิ์ที่ให้กับ role รายตัว** ข้อ 2 จึงยังอยู่

## ผลกระทบจริง

| ฟังก์ชัน | ทำอะไรได้ |
| --- | --- |
| `list_chaseable_participants()` | **คืน `line_user_id` · `amount_due_thb` · `user_id` ของคนค้างจ่าย** ใครมี anon key ก็อ่านได้ — ข้อมูลส่วนบุคคลรั่ว |
| `mark_no_shows()` | ตัดเครดิตคนไม่มาตามนัด |
| `close_unfilled_tournaments()` | ยกเลิกงานพร้อมคืนเงิน |
| `record_chase()` | บันทึกการทวงเงิน |
| อีกสี่ตัว | เปลี่ยนสถานะหรือคำนวณใหม่ |

ทุกตัวยกเว้นตัวแรกมีเงื่อนไขเวลาคุมอยู่ และ cron ยิงทุกห้านาที จึงเร่งได้แค่ไม่กี่นาที
**ไม่ใช่ทำสิ่งที่ทำไม่ได้อยู่แล้ว** ส่วนตัวแรกเป็นการอ่านข้อมูลที่ไม่ควรอ่านได้จริง ๆ

## Scope

- migration revoke แปดตัวนั้นจาก `public, anon, authenticated`
- `supabase/tests/machine_rpc_grants.test.sql` — ปักสิทธิ์ของ 27 ฟังก์ชันที่ปิดในเครื่อง
- `scripts/check-grants.mjs` + `npm run check:grants` — ตัวจับการเบี่ยงข้ามสภาพแวดล้อม

## Decisions

### ไม่แตะ `service_role`

ดัมป์บอกว่า production มี grant ให้ `service_role` เกินในเครื่องอยู่สิบเอ็ดตัว
แต่ถอดผิดตัวเดียวคือ cron ล่มทั้งระบบ ส่วนที่เป็นความปลอดภัยจริงคือ `anon`
กับ `authenticated` ซึ่งตั๋วนี้ปิดครบ

### ไม่รันลูปปิดประตูใหม่ทั้งระบบ

ทำได้และแก้ได้ทั้งตระกูล แต่ต้องเขียนรายชื่อฟังก์ชันที่ผู้ใช้เรียกได้ใหม่หกสิบกว่าตัว
ตกไปตัวเดียวคือผู้ใช้บน production ใช้งานไม่ได้ทันที เป้าหมายของตั๋วนี้คือ
**ทำให้ production ตรงกับในเครื่อง** ไม่ใช่ออกแบบสิทธิ์ใหม่

### `from public` ไม่ใช่แค่ `from anon, authenticated`

ฟังก์ชันที่ยังไม่มี ACL ถือว่า PUBLIC เรียกได้ ถ้า revoke แค่สองบทบาทนั้น
ACL จะถูกสร้างขึ้นพร้อมสิทธิ์ของ PUBLIC ที่ค้างอยู่ แล้ว `has_function_privilege`
ก็ยังตอบว่าเรียกได้ — เจอจริงตอนเขียนตั๋วนี้ รอบแรกเทสแดงสามข้อด้วยเหตุนี้

### ตัวจับการเบี่ยงเป็นสคริปต์ ไม่ใช่ pgTAP

`supabase test db --linked` ล้มตั้งแต่ `select plan(...)` เพราะ production ไม่ได้
ติดตั้ง `pgtap` (เป็นส่วนขยายฝั่ง dev) การติดตั้งลง production เพื่อรันเทสเป็น
การเพิ่มผิวที่ต้องดูแลโดยไม่จำเป็น สคริปต์อ่านดัมป์แทนจึงไม่ต้องติดตั้งอะไรเพิ่ม

## Review Notes — 20 ก.ย. 2569

### ผมนับผิดกลางทางแล้วแก้

รอบแรกเขียนสคริปต์ให้เทียบ **บรรทัด GRANT/REVOKE ในดัมป์** ของสองฝั่งตรง ๆ
ได้ผลว่าเบี่ยง 47 ฟังก์ชัน และผมรายงานตัวเลขนั้นออกไปแล้ว

ตัวเลขนั้นผิด เพราะฟังก์ชันที่ยังไม่มี ACL **ไม่มีบรรทัดอะไรเลยในดัมป์** ทั้งที่
PUBLIC เรียกได้ การไม่มีบรรทัดจึงถูกนับเป็น "ปิด" ในเครื่องและ "เปิด" บน production
ทั้งที่จริงเปิดทั้งคู่ ผมเกือบเขียน migration ที่ revoke 46 ตัว ซึ่งจะปิดฟังก์ชันที่
ผู้ใช้ต้องเรียก 38 ตัวไปด้วย — จับได้เพราะรัน `db reset` แล้วนับฟังก์ชันที่ยังเปิดอยู่
ในเครื่อง เหลือ 28 จาก 66

ฐานที่ถูกคือ **สิทธิ์ที่มีผลจริง** — ฝั่งในเครื่องถาม `has_function_privilege`
จากฐานข้อมูลตรง ๆ ส่วนฝั่ง production อ่านดัมป์ด้วยกติกา "มี GRANT ให้
anon/authenticated **หรือ** ไม่มีบรรทัด ACL เลย = เปิด" แล้วได้ 8 ตัวตามเดิม

### สิ่งที่ยังไม่ได้แก้

- ฟังก์ชันที่ **เปิดทั้งสองฝั่ง** ยังไม่ได้ไล่ดูว่าควรเปิดจริงไหม 66 ตัวนั้นรวม
  RPC ที่เช็ก `auth.uid()` เองอยู่แล้ว แต่ก็รวมของที่อาจไม่ควรเปิดให้ `anon`
  ต้องเป็นตั๋วของตัวเองที่ไล่ทีละตัว
- `npm run check:grants` ยังต้องเรียกเอง ยังไม่มี CI รันให้
