# LSN-0003 — Row Level Security policies

**Type:** Feature · **Phase:** 1 · **Status:** Done

## Goal
Enforce role-based access entirely in the database, not in the UI.

## Acceptance criteria
- [x] RLS enabled on every application table.
- [x] SECURITY DEFINER helpers: `is_platform_admin`, `is_venue_member`,
      `is_session_organizer`, `is_session_participant` (no policy recursion).
- [x] Players read only their own participation, payments, refunds, notifications.
- [x] Organizers manage only sessions they created.
- [x] Venue admins manage only venues they are a member of.
- [x] Platform admins read everything; writes still go through RPCs.
- [x] Anonymous users can read published (`open`/`ready_to_book`/`booked`) sessions
      and active venues/courts only.

## Review notes
- **Policy recursion.** `sessions_read` consulted `bookings`, whose policy
  consulted `sessions` — Postgres raised "infinite recursion detected in policy".
  Broken with three SECURITY DEFINER helpers (`session_is_published`,
  `session_has_public_booking`, `is_booking_venue_member`).
- **Missing table grants.** RLS filters rows a role may already touch; without
  `GRANT` the policies were unreachable. Added explicit grants for
  `anon`/`authenticated`, and for `service_role`, which bypasses RLS but is
  still subject to table privileges — its absence made every admin-client read
  silently return nothing.
- **`join_session` was locked out.** It is deliberately called with the player's
  own client so `auth.uid()` applies, so it had to be added to the execute
  allow-list. Verified that the money and court RPCs remain service-role only.
- Isolation verified per role: anon sees only published sessions, a player sees
  only their own payments and contact row, a venue admin sees only their venue,
  and self-promotion to platform_admin is rejected by trigger.
