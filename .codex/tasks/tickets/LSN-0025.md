# 🟢 LSN-0025 — ผู้จัดยืนยันคอร์ตเอง

**Type:** Feature · **Phase:** 9 · **Status:** Backlog
**Source:** `docs/product-concept.md` หัวข้อ "เรื่องคอร์ต — คำถามที่ทำให้โปรดักต์นี้ตายได้"
**Depends on:** LSN-0021 (การคิดเงินจากราคาคอร์ต) — merge แล้ว

## Goal

ผู้จัดกดปุ่ม "ได้คอร์ตแล้ว" แล้วก๊วนกลายเป็น `booked` ได้ **โดยไม่ต้องมีสนามพันธมิตร**

นี่คือช่องว่างเดียวที่ขวางอยู่ระหว่าง MVP ที่เอกสารแนวคิดประกาศไว้ กับสิ่งที่ระบบ
ทำได้จริงวันนี้

## Context

ตรวจโค้ดแล้ว **มีเพียงสองทาง**ที่ทำให้ก๊วนกลายเป็น `booked`:

| ทาง | ที่ | เงื่อนไข |
| --- | --- | --- |
| `request_booking()` | `20260901000200_functions.sql:826` | สนามต้องเปิด `auto_confirm_bookings` |
| `venue_decide_booking()` | `20260901000200_functions.sql:883` | กั้นด้วย `is_venue_member()` |

ทั้งสองทางต้องมีคนฝั่งสนาม **ผู้จัดจึงยืนยันคอร์ตของตัวเองไม่ได้เลย** ทั้งที่ผู้จัด
ก๊วนแบดส่วนใหญ่มีคอร์ตประจำที่โทรจองเองอยู่แล้ว

**ครึ่งหลังมีอยู่แล้ว** — `settle_session_costs()` รองรับกรณี "สนามยืนยันทางโทรศัพท์
และไม่มีอะไรถูกจองในแอป" ไว้เรียบร้อย โดย comment ในโค้ดเขียนไว้ตรง ๆ ว่าให้ใช้
ราคาคอร์ตที่ถูกที่สุดที่ผู้จัดอนุมัติไว้เป็นฐานคิดเงิน ตั๋วนี้จึงเติมเฉพาะครึ่งแรก

**ข้อเท็จจริงอื่นที่ตรวจแล้ว:**

- `bookings.venue_id` และ `bookings.court_id` เป็น **NOT NULL** ทั้งคู่ —
  นี่คือข้อจำกัดจริงข้อเดียวของตั๋วนี้ ดู Open Questions
- `bookings.price_thb` เป็น **NOT NULL** ผู้จัดจึงต้องกรอกราคาที่จ่ายจริง
  ไม่งั้นการคิดเงินจะไม่มีฐาน
- `bookings_read` policy ใช้ `is_session_organizer(session_id)` อยู่แล้ว
  ผู้จัดจึงเห็นแถวของตัวเองได้โดยไม่ต้องแก้ RLS แม้ `venue_id` จะว่าง
- `booking_status` enum มีค่า `confirmed` อยู่แล้ว ไม่ต้องเพิ่ม
- ทุกวันนี้ **ไม่มีการแจ้งเตือนผู้เล่นตอนได้คอร์ต** ทั้งสองทางเขียนแค่ `app_log`
  ผู้เล่นรู้จากการเปิดลิงก์ ซึ่งมี realtime อยู่แล้ว

## Scope

- RPC `confirm_court_manually()` ให้ผู้จัดบันทึกคอร์ตที่หามาเอง แล้วย้ายก๊วนไป `booked`
- ปุ่มฝั่งผู้จัดบนหน้าจัดการก๊วน พร้อมช่องกรอกชื่อสนามและราคาที่จ่ายจริง
- เขียน `audit_logs` ทั้ง `booking.confirmed` และ `session.booked` ให้ครบตามที่
  Definition of Done กำหนด
- pgTAP ปักขอบเขตสิทธิ์และ allowlist ของสถานะ

## Non-goals

- ไม่แตะทางของสนามพันธมิตรทั้งสองทางที่มีอยู่
- ไม่ทำ UI ให้สนามที่ไม่ได้เป็นพันธมิตรเข้ามาใช้
- ไม่เพิ่มการแจ้งเตือนตอนได้คอร์ต — ทางที่มีอยู่ก็ไม่แจ้ง ถ้าจะเพิ่มควรเพิ่มพร้อมกัน
  ทั้งสามทางในตั๋วแยก
- ไม่ทำการยกเลิกคอร์ตที่ยืนยันเอง — ใช้การยกเลิกก๊วนที่มีอยู่แล้ว

## สถานะไหนยืนยันได้ — allowlist ไม่ใช่ denylist

ด้วยเหตุผลเดียวกับบั๊กที่เคยเจอใน LSN-0020:

| สถานะ | ยืนยันได้ | เพราะ |
| --- | --- | --- |
| `ready_to_book` | ✅ | คนครบ เงินครบแล้ว เหลือแค่คอร์ต |
| `booking_failed` | ✅ | ระบบลองแล้วไม่ได้ ผู้จัดไปหามาเอง — เป็นเคสที่ตั๋วนี้มีไว้เพื่อ |
| `holding_court` | ❌ | มีคอร์ตที่กันไว้ค้างอยู่ ต้องปล่อยก่อน ไม่งั้นจะมีสองการจอง |
| `open` / `draft` / `ready_to_book` ก่อนเงินครบ | ❌ | **เงินยังไม่ครบ** การยอมให้ยืนยันตรงนี้คือการทำลายคำสัญญาหลักของโปรดักต์ |
| `booked` / `cancelled` / `completed` | ❌ | จบไปแล้ว |

## Acceptance Criteria

- [ ] ผู้จัดกดยืนยันคอร์ตจาก `ready_to_book` แล้วก๊วนเป็น `booked` — ปักด้วยเทส
- [ ] ผู้จัดกดยืนยันคอร์ตจาก `booking_failed` แล้วก๊วนเป็น `booked` และ
      `failure_reason` ถูกล้าง — ปักด้วยเทส
- [ ] สถานะนอก allowlist ถูกปฏิเสธทุกตัว รวม `open` ที่เงินยังไม่ครบ — ปักด้วยเทส
- [ ] คนที่ไม่ใช่ผู้จัดก๊วนนั้นเรียกไม่ได้ — ปักด้วยเทส
- [ ] ราคาที่ผู้จัดกรอกกลายเป็นฐานคิดเงินจริง: `settle_session_costs()` ต้องใช้ราคานั้น
      ไม่ใช่ราคาคอร์ตที่อนุมัติไว้ — ปักด้วยเทส **ข้อนี้คือข้อที่พิสูจน์ว่าตั๋วนี้ต่อกับ
      LSN-0021 ได้จริง**
- [ ] เขียน `audit_logs` ทั้ง `booking.confirmed` และ `session.booked` โดย
      **from-state เป็นสถานะจริง** ไม่ใช่ `'holding_court'` ที่ hardcode ไว้ในทางเดิม
- [ ] pgTAP ของ LSN-0021 และ LSN-0023 ยังเขียวโดยไม่ต้องแก้เทส
- [ ] ปุ่มบนหน้าจัดการก๊วนขึ้นเฉพาะสถานะที่ยืนยันได้ ไม่ใช่ขึ้นแล้ว disabled
- [ ] ราคาที่กรอกต้องมากกว่า 0 และถูกปฏิเสธที่ระดับฐานข้อมูลถ้าไม่ใช่

## Open Questions

### 1. จะบันทึกคอร์ตที่ไม่ได้อยู่ในระบบยังไง — ต้องตัดสินก่อน `/kanban start`

`bookings.venue_id` และ `bookings.court_id` เป็น NOT NULL แต่คอร์ตที่ผู้จัด
โทรจองเองมักไม่มีอยู่ในตาราง `venues`/`courts` ของเรา (ตอนนี้มีสนามที่ไม่มี
`venue_members` อยู่ **0 แห่ง** ทุกสนามในฐานข้อมูลถูกสร้างมาพร้อมสมาชิก)

| ทาง | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| **ก. ทำให้ `venue_id`/`court_id` เป็น nullable** | ตรงไปตรงมา ไม่ต้องสร้างข้อมูลปลอม | แก้คอลัมน์ NOT NULL ที่มีอยู่ |
| ข. ให้ผู้จัดเลือกสนามจากรายการที่มี | ไม่แตะสคีมา | ใช้ไม่ได้กับสนามที่เราไม่รู้จัก ซึ่งคือเคสหลักของตั๋วนี้ |
| ค. ไม่สร้างแถว `bookings` เลย เก็บเป็นโน้ตบน `sessions` | เบาที่สุด | `settle_session_costs()` อ่านราคาจาก `bookings` ต้องแก้ LSN-0021 ซึ่งมี pgTAP ปักไว้ 8 ข้อ |

**เสนอทาง ก.** เพราะวัดผลกระทบแล้วเล็กกว่าที่คิด — มีผู้อ่านสองคอลัมน์นี้เพียง
4 แห่ง และสามแห่งแรกรับ null ได้โดยพฤติกรรมยังถูก:

| ที่ | พฤติกรรมเมื่อ null |
| --- | --- |
| `rls_helpers.sql:160` `is_booking_venue_member` | คืน false — **ถูกแล้ว** ไม่มีสนามไหนควรมาตัดสินการจองที่ผู้จัดทำเอง |
| `functions.sql:205` เช็คคอร์ตว่าง | ไม่ match — **ถูกแล้ว** คอร์ตนอกระบบไม่ควรไปกันคิวคอร์ตในระบบ |
| `functions.sql:868` gate ของ `venue_decide_booking` | เข้าไม่ได้ — **ถูกแล้ว** |
| `src/app/admin/venues/page.tsx:31` รวมรายได้ตาม `venue_id` | **ต้องแก้** ให้ข้ามแถวที่ไม่มีสนาม |

ส่วนชื่อสนามที่ผู้จัดพิมพ์ ให้เก็บเป็น text บน `bookings` (เช่น `manual_venue_name`)
เพื่อให้ใบสรุปและหน้าก๊วนมีอะไรแสดง

**ถ้าเกรพเลือกทางอื่น ให้แก้ตรงนี้ก่อนเริ่ม** — ทางเลือกนี้เปลี่ยนสคีมา จึงไม่ควร
ตัดสินระหว่างเขียนโค้ด

### 2. ผู้จัดโกหกว่าได้คอร์ตแล้ว จะเอายังไง

เอกสารแนวคิดบันทึกเป็นความเสี่ยงไว้แล้ว ตั๋วนี้ **ไม่แก้** และเสนอให้ไม่แก้ในรอบนี้
เพราะกลไกที่มีอยู่รองรับผลเสียแล้ว: ผู้เล่นยกเลิกได้และได้เงินคืนตามนโยบายของ
LSN-0019 ส่วนพฤติกรรมซ้ำของผู้จัดจะเห็นได้จาก `audit_logs`

ถ้าจะกันจริงในอนาคต ทางที่สมเหตุสมผลคือให้ผู้เล่นคนใดคนหนึ่งยืนยันรับทราบ
ซึ่งเป็นงานคนละใบ
