# 🟢 LSN-0025 — ผู้จัดยืนยันคอร์ตเอง

**Type:** Feature · **Phase:** 9 · **Status:** done
**Source:** `docs/product-concept.md` หัวข้อ "เรื่องคอร์ต — คำถามที่ทำให้โปรดักต์นี้ตายได้"
**Depends on:** LSN-0021 (การคิดเงินจากราคาคอร์ต) — merge แล้ว

## Goal

ผู้จัดกดปุ่ม "ได้คอร์ตแล้ว" แล้วก๊วนกลายเป็น `booked` ได้ **โดยไม่ต้องมีสนามพันธมิตร**

นี่คือช่องว่างเดียวที่ขวางอยู่ระหว่าง MVP ที่เอกสารแนวคิดประกาศไว้ กับสิ่งที่ระบบ
ทำได้จริงวันนี้

## Context

ตรวจโค้ดแล้ว **มีเพียงสองทาง**ที่ทำให้ก๊วนกลายเป็น `booked`:

| ทาง | ที่ | เงื่อนไข |
| --- | --- | --- |
| `request_booking()` | `20260901000200_functions.sql:826` | สนามต้องเปิด `auto_confirm_bookings` |
| `venue_decide_booking()` | `20260901000200_functions.sql:883` | กั้นด้วย `is_venue_member()` |

ทั้งสองทางต้องมีคนฝั่งสนาม **ผู้จัดจึงยืนยันคอร์ตของตัวเองไม่ได้เลย** ทั้งที่ผู้จัด
ก๊วนแบดส่วนใหญ่มีคอร์ตประจำที่โทรจองเองอยู่แล้ว

**ครึ่งหลังมีอยู่แล้ว** — `settle_session_costs()` รองรับกรณี "สนามยืนยันทางโทรศัพท์
และไม่มีอะไรถูกจองในแอป" ไว้เรียบร้อย โดย comment ในโค้ดเขียนไว้ตรง ๆ ว่าให้ใช้
ราคาคอร์ตที่ถูกที่สุดที่ผู้จัดอนุมัติไว้เป็นฐานคิดเงิน ตั๋วนี้จึงเติมเฉพาะครึ่งแรก

**ข้อเท็จจริงอื่นที่ตรวจแล้ว:**

- `bookings.venue_id` และ `bookings.court_id` เป็น **NOT NULL** ทั้งคู่ —
  นี่คือข้อจำกัดจริงข้อเดียวของตั๋วนี้ ตัดสินแล้วให้เป็น nullable ดูหัวข้อ Decisions
- `bookings.price_thb` เป็น **NOT NULL** ผู้จัดจึงต้องกรอกราคาที่จ่ายจริง
  ไม่งั้นการคิดเงินจะไม่มีฐาน
- `bookings_read` policy ใช้ `is_session_organizer(session_id)` อยู่แล้ว
  ผู้จัดจึงเห็นแถวของตัวเองได้โดยไม่ต้องแก้ RLS แม้ `venue_id` จะว่าง
- `booking_status` enum มีค่า `confirmed` อยู่แล้ว ไม่ต้องเพิ่ม
- ทุกวันนี้ **ไม่มีการแจ้งเตือนผู้เล่นตอนได้คอร์ต** ทั้งสองทางเขียนแค่ `app_log`
  ผู้เล่นรู้จากการเปิดลิงก์ ซึ่งมี realtime อยู่แล้ว

## Scope

- RPC `confirm_court_manually()` ให้ผู้จัดบันทึกคอร์ตที่หามาเอง แล้วย้ายก๊วนไป `booked`
- ปุ่มฝั่งผู้จัดบนหน้าจัดการก๊วน พร้อมช่องกรอกชื่อสนามและราคาที่จ่ายจริง
- เขียน `audit_logs` ทั้ง `booking.confirmed` และ `session.booked` ให้ครบตามที่
  Definition of Done กำหนด
- pgTAP ปักขอบเขตสิทธิ์และ allowlist ของสถานะ

## Non-goals

- ไม่แตะทางของสนามพันธมิตรทั้งสองทางที่มีอยู่
- ไม่ทำ UI ให้สนามที่ไม่ได้เป็นพันธมิตรเข้ามาใช้
- ไม่เพิ่มการแจ้งเตือนตอนได้คอร์ต — ทางที่มีอยู่ก็ไม่แจ้ง ถ้าจะเพิ่มควรเพิ่มพร้อมกัน
  ทั้งสามทางในตั๋วแยก
- ไม่ทำการยกเลิกคอร์ตที่ยืนยันเอง — ใช้การยกเลิกก๊วนที่มีอยู่แล้ว

## สถานะไหนยืนยันได้ — allowlist ไม่ใช่ denylist

ด้วยเหตุผลเดียวกับบั๊กที่เคยเจอใน LSN-0020:

| สถานะ | ยืนยันได้ | เพราะ |
| --- | --- | --- |
| `ready_to_book` | ✅ | คนครบ เงินครบแล้ว เหลือแค่คอร์ต |
| `booking_failed` | ✅ | ระบบลองแล้วไม่ได้ ผู้จัดไปหามาเอง — เป็นเคสที่ตั๋วนี้มีไว้เพื่อ |
| `holding_court` | ❌ | มีคอร์ตที่กันไว้ค้างอยู่ ต้องปล่อยก่อน ไม่งั้นจะมีสองการจอง |
| `open` / `draft` | ❌ | **เงินยังไม่ครบ** การยอมให้ยืนยันตรงนี้คือการทำลายคำสัญญาหลักของโปรดักต์ — `ready_to_book` ปลอดภัยเพราะสถานะนั้นแปลว่าคนและเงินครบแล้วโดยนิยาม |
| `booked` / `cancelled` / `completed` | ❌ | จบไปแล้ว |

## Decisions — ตัดสินครบแล้ว ไม่มีข้อค้าง

### 1. จะบันทึกคอร์ตที่ไม่ได้อยู่ในระบบยังไง → **ทาง ก. ทำให้ nullable** ✅ ตัดสินแล้ว 12 ก.ย.

เกรพเลือกทาง ก. — `bookings.venue_id` และ `bookings.court_id` กลายเป็น nullable
และคอร์ตที่ผู้จัดหามาเองถูกบันทึกเป็นแถว `bookings` ที่ไม่ผูกกับสนามในระบบ

**ทางที่ไม่ได้เลือก และเหตุผล:**

| ทาง | ทำไมไม่เลือก |
| --- | --- |
| ข. ให้เลือกสนามจากรายการที่มี | ใช้ไม่ได้กับสนามที่เราไม่รู้จัก ซึ่งคือเคสหลักของตั๋วนี้ |
| ค. ไม่สร้างแถว `bookings` เก็บเป็นโน้ตบน `sessions` | `settle_session_costs()` อ่านราคาจาก `bookings` จะต้องแก้ LSN-0021 ซึ่งมี pgTAP ปักไว้ 8 ข้อ |

**เหตุผลที่เลือกทาง ก.** วัด blast radius แล้วมีผู้อ่านสองคอลัมน์นี้เพียง 4 แห่ง
และสามแห่งแรกรับ null ได้โดยพฤติกรรมยังถูก:

| ที่ | พฤติกรรมเมื่อ null | ต้องแก้ไหม |
| --- | --- | --- |
| `rls_helpers.sql:160` `is_booking_venue_member` | คืน false — ไม่มีสนามไหนควรมาตัดสินการจองที่ผู้จัดทำเอง | ไม่ |
| `functions.sql:205` เช็คคอร์ตว่าง | ไม่ match — คอร์ตนอกระบบไม่ควรไปกันคิวคอร์ตในระบบ | ไม่ |
| `functions.sql:868` gate ของ `venue_decide_booking` | เข้าไม่ได้ | ไม่ |
| `src/app/admin/venues/page.tsx:25-32` รวมรายได้ตาม `venue_id` | ไม่พัง แต่ได้ Map ที่มีคีย์ `null` ซึ่งไม่มีใครอ่าน = ข้อมูลตายเงียบ ๆ และ type ประกาศไว้ว่า `venue_id: string` ซึ่งจะกลายเป็นคำโกหก | **ใช่** |

### สิ่งที่ต้องทำเพิ่มจากการตัดสินนี้

1. **Migration** เปลี่ยน `bookings.venue_id` และ `bookings.court_id` เป็น nullable
2. **เพิ่มคอลัมน์ `manual_venue_name text`** บน `bookings` สำหรับชื่อสนามที่ผู้จัดพิมพ์
   เพื่อให้หน้าก๊วนและใบสรุปมีอะไรแสดง
3. **check constraint** ที่บังคับว่าแถวหนึ่งต้องเป็นอย่างใดอย่างหนึ่งชัดเจน ไม่ใช่ครึ่ง ๆ:
   ```sql
   check (
     (venue_id is not null and court_id is not null and manual_venue_name is null)
     or
     (venue_id is null and court_id is null and manual_venue_name is not null)
   )
   ```
   ข้อนี้สำคัญกว่าที่ดู — ถ้าไม่มี จะมีแถวที่มี `venue_id` แต่ไม่มี `court_id` โผล่มา
   ทีหลังโดยไม่มีใครตั้งใจ แล้วไม่มีใครรู้ว่าควรอ่านยังไง
4. **แก้ `src/app/admin/venues/page.tsx`** เปลี่ยน type เป็น `venue_id: string | null`
   แล้วข้ามแถวที่เป็น null อย่างชัดเจน ไม่ใช่ปล่อยให้ตกลง Map เงียบ ๆ
5. **เทสที่ปัก check constraint** ว่าแถวครึ่ง ๆ ถูกปฏิเสธจริง — ปักด้วย `throws_ok`

  p_session_id  uuid,
  p_venue_name  text,
  p_price_thb   integer
) returns jsonb
language plpgsql security definer
set search_path = public, pg_temp
as $$
declare
  v_session public.sessions%rowtype;
  v_from    text;
  v_id      uuid;
begin
  select * into v_session from public.sessions where id = p_session_id for update;
  if v_session.id is null then
    return jsonb_build_object('ok', false, 'reason', 'session_not_found');
  end if;
  if not public.is_session_organizer(p_session_id) then
    return jsonb_build_object('ok', false, 'reason', 'not_organizer');
  end if;

  -- allowlist ไม่ใช่ denylist ด้วยเหตุผลเดียวกับบั๊ก LSN-0020
  --
  -- แถวที่สำคัญที่สุดของด่านนี้คือแถวที่ปฏิเสธ `open`: ตอนนั้นเงินยังไม่ครบ
  -- การยอมให้ยืนยันคอร์ตตรงนั้นคือการทำลายคำสัญญาหลักของโปรดักต์ด้วยปุ่มเดียว
  -- ส่วน holding_court ถูกปฏิเสธเพราะมีคอร์ตที่กันไว้ค้างอยู่ ต้องปล่อยก่อน
  if v_session.status not in ('ready_to_book', 'booking_failed') then
    return jsonb_build_object('ok', false, 'reason', 'session_not_ready');
  end if;

  if p_price_thb is null or p_price_thb <= 0 then
    return jsonb_build_object('ok', false, 'reason', 'invalid_amount');
  end if;
  if p_venue_name is null or length(btrim(p_venue_name)) = 0 then
    return jsonb_build_object('ok', false, 'reason', 'venue_name_required');
  end if;

  v_from := v_session.status::text;

  -- idempotency_key เป็น UNIQUE อยู่แล้ว การกดซ้ำจึงชนกันเองโดยไม่ต้องเขียน guard
  insert into public.bookings
    (session_id, manual_venue_name, starts_at, ends_at, status,
     price_thb, attempt_no, idempotency_key, confirmed_at, decided_by)
  values
    (p_session_id, btrim(p_venue_name), v_session.starts_at, v_session.ends_at,
     'confirmed', p_price_thb, 1, 'manual:' || p_session_id::text, now(), auth.uid())
  returning id into v_id;

  update public.sessions
  set status = 'booked', booking_id = v_id, failure_reason = null
  where id = p_session_id;

  perform public.app_log(auth.uid(), 'booking', v_id, p_session_id,
    'booking.confirmed', null, 'confirmed',
    jsonb_build_object('manualVenueName', btrim(p_venue_name),
                       'priceThb', p_price_thb, 'manual', true));

  -- from-state เป็นสถานะจริง ไม่ใช่ 'holding_court' ที่ hardcode ไว้ในทางเดิม
  -- เพราะทางนี้มาจาก ready_to_book หรือ booking_failed
  perform public.app_log(auth.uid(), 'session', p_session_id, p_session_id,
    'session.booked', v_from, 'booked',
    jsonb_build_object('bookingId', v_id, 'manual', true));

  return jsonb_build_object('ok', true, 'bookingId', v_id, 'priceThb', p_price_thb);
exception when unique_violation then

end;
$$;

allowlist มีแค่ `ready_to_book` กับ `booking_failed` การยอมให้ยืนยันคอร์ตตอน
สถานะ `open` แปลว่าเงินยังไม่ครบ ซึ่งคือการทำลายคำสัญญาหลักของโปรดักต์ด้วยปุ่มเดียว
ใช้ allowlist ไม่ใช่ denylist ด้วยเหตุผลเดียวกับบั๊ก LSN-0020

Falsify แล้วทั้ง 5 แบบ: ถอด allowlist → แดง 3 ข้อ · เปลี่ยนเป็น denylist → แดง 3 ข้อ ·
ถอด `is_session_organizer` → แดง 1 · ไม่ล้าง `failure_reason` → แดง 1 ·
ใส่ราคาคงที่แทนค่าที่รับมา → แดง 1

**2. สอง nullable พร้อมกันเปิดรูปแถวที่ไม่มีความหมาย**

`venue_id` กับ `court_id` ว่างได้แล้ว ซึ่งเปิดรูปแถวขึ้นมาสี่แบบ สองแบบไร้ความหมาย
`bookings_venue_shape` บังคับว่าแถวหนึ่งต้องเป็นอย่างใดอย่างหนึ่งชัดเจน ถ้าไม่มี
จะมีแถวที่มีสนามแต่ไม่มีคอร์ตโผล่มาทีหลังโดยไม่มีใครตั้งใจ

และ `bookings_price_thb_check` เดิมยอม `>= 0` จึงต้องมี
`bookings_manual_price_positive` เป็นของตัวเอง ไม่งั้นเกณฑ์ราคา > 0 จะไม่มีอะไรบังคับ

**3. `bookings_no_overlap` ใช้ `court_id WITH =`**

`court_id` ว่างจึงไม่มีวันชน — คอร์ตนอกระบบไม่ไปกันคิวคอร์ตในระบบ **ถูกแล้ว**
และปักด้วยเทสที่แทรกสองแถวเวลาทับกันสนิทแล้วต้องผ่าน

**4. เปลี่ยน reason code เพราะของเดิมชนกับ orchestrator**

ตอนแรก RPC คืน `session_not_ready` ซึ่งมีอยู่แล้ว —
`booking-eligibility.ts` ประกาศเป็น typed reason และ `book-session.ts:254`
มี logic แยกตามค่านี้ การใช้ซ้ำจะทำให้ข้อความเดียวรับใช้สองด่านที่ไม่เกี่ยวกัน
เปลี่ยนเป็น `court_confirm_not_allowed`

**5. แตะ state machine ที่มีเทสปักไว้**

`tests/state-machines.test.ts` เดิมปักว่า `ready_to_book → booked` ต้องเป็น false
ภายใต้ชื่อ `'refuses to skip the holding step'` — เกรพตัดสินให้เปิดทางแล้วแก้เทส
ให้ตรงกติกาใหม่ เทสใหม่ยืนยันสองอย่าง: ข้ามขั้น holding ได้ **แต่ `open → booked`
ยังปิดตลอดกาล**

**หมายเหตุ:** ตาราง `SESSION_TRANSITIONS` เป็นเอกสารมากกว่าด่านบังคับ
มีผู้เรียก `assertSessionTransition` ที่เดียวและไม่ได้อยู่บนเส้นทางนี้
ด่านจริงคือ allowlist ใน SQL
