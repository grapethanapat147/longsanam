# 🔴 LSN-0043 — ผู้ใช้ตั้งนัดไม่ได้เลย เพราะ trigger สร้างรหัสนัดไม่มีสิทธิ์

**Type:** Bugfix · **Phase:** 10 · **Status:** Done
**Source:** เจอตอนตรวจ LSN-0042 บนเบราว์เซอร์

## อาการ

กด "เผยแพร่นัด" แล้วขึ้น **"เกิดข้อผิดพลาดที่ไม่คาดคิด กรุณาลองใหม่อีกครั้ง"**
ทุกครั้ง ไม่ว่ากรอกอะไร นัดไม่ถูกสร้าง

**นี่คือเส้นทางหลักของโปรดักต์** — ตั้งนัดไม่ได้แปลว่าใช้อะไรไม่ได้เลย

## ต้นตอ

```
code:    42501
message: permission denied for function generate_session_code
```

`sessions` มี trigger `sessions_assign_code` ที่เรียก `generate_session_code()`
เพื่อสร้างรหัสแชร์ตอน insert ทั้งสองฟังก์ชันเป็น **INVOKER** และ
`generate_session_code()` grant ให้แค่ `postgres` กับ `service_role`

trigger ทำงานในสิทธิ์ของคนที่ insert ซึ่งคือ `authenticated` เพราะ**นัดถูก insert
ตรงจากฝั่งไคลเอนต์ผ่าน PostgREST ไม่ได้ผ่าน RPC** จึงโดนปฏิเสธทุกครั้ง

### ทำไมก๊วนกับทัวร์นาเมนต์ไม่เจอปัญหานี้

`generate_group_code()` และ `generate_tournament_code()` ก็เป็น INVOKER และไม่มี
ACL เหมือนกัน **แต่ถูกเรียกจาก `create_group()` / `create_tournament()` ซึ่งเป็น
`security definer`** โค้ดจึงทำงานในสิทธิ์เจ้าของ ไม่ใช่สิทธิ์ผู้ใช้

ความต่างอยู่ที่ **ทางเข้า** ไม่ใช่ที่ตัวฟังก์ชัน — นัดเป็นของเดียวที่ insert ตรง

### ทำไมไม่มีใครเห็นมานาน

1. `seed.sql` สร้างนัดในสิทธิ์ `postgres` จึงผ่านเสมอ
2. pgTAP ที่มีอยู่ insert ในสิทธิ์ `postgres` เหมือนกัน
3. **`createSessionAction` กลืน error ของฐานข้อมูลทิ้งเงียบ ๆ** แล้วคืนข้อความ
   "เกิดข้อผิดพลาดที่ไม่คาดคิด" โดยไม่ log อะไรเลย จึงไม่มีร่องรอยให้ตามด้วยซ้ำ

## Scope

- ทำให้ `sessions_assign_code()` และ `generate_session_code()` เป็น `security definer`
  พร้อม `set search_path`
- **log error ของฐานข้อมูลใน `createSessionAction`** แทนที่จะกลืนทิ้ง
- pgTAP ที่ insert นัด **ในสิทธิ์ `authenticated` จริง** แล้วยืนยันว่าได้รหัสนัด

## Decisions

### `security definer` ไม่ใช่ `grant execute to authenticated`

การ grant ก็แก้อาการได้ แต่ `generate_session_code()` วนหารหัสที่ยังไม่ซ้ำด้วย
`not exists (select 1 from public.sessions where public_code = v_code)`
ซึ่งอ่านผ่าน RLS ของผู้เรียก **ผู้ใช้ทั่วไปมองไม่เห็นนัดของคนอื่นทั้งหมด**
จึงอาจได้รหัสที่ซ้ำกับนัดที่ตัวเองมองไม่เห็น แล้วไปตายที่ unique constraint แทน

`security definer` แก้ทั้งสิทธิ์และความถูกต้องของการตรวจซ้ำในคราวเดียว

### log error ไว้ด้วย ไม่ใช่แค่แก้บั๊ก

ที่บั๊กนี้อยู่ได้นานเพราะ action กลืน error ทิ้ง ถ้าไม่แก้จุดนั้น บั๊กหน้าตาแบบ
เดียวกันจะซ่อนตัวได้อีก

## Acceptance Criteria

- [x] insert นัดในสิทธิ์ `authenticated` สำเร็จ และได้ `public_code` อัตโนมัติ · ปักด้วย pgTAP
- [x] **falsify** — คืนเป็น INVOKER แล้วเทสต้องแดง
- [x] `createSessionAction` log error ของฐานข้อมูลเมื่อ insert ล้ม
- [x] ตั้งนัดได้จริงจนจบบนเบราว์เซอร์
- [x] เทสเดิมเขียวทั้งหมด

### ทำไมเทสเดิมทั้งชุดถึงไม่จับ

เทสเดิมทุกไฟล์ insert นัดในสิทธิ์ `postgres` ซึ่ง**ผ่านเสมอ** ส่วนผู้ใช้จริงเป็น
`authenticated` เทสใหม่จึงต้องสวมบทบาทให้ถูก มิฉะนั้นมันจะเขียวโดยไม่ได้เฝ้าอะไรเลย
— รูปแบบ "เทสที่ดูเหมือนเฝ้าแต่ไม่ได้เฝ้า" แบบเดียวกับที่เจอใน LSN-0022 · LSN-0024
· LSN-0035

### สิ่งที่แก้เพิ่มนอกจากตัวบั๊ก

`createSessionAction` **กลืน error ของฐานข้อมูลทิ้งเงียบ ๆ** แล้วคืนข้อความ
"เกิดข้อผิดพลาดที่ไม่คาดคิด" โดยไม่ log อะไรเลย นั่นคือเหตุผลที่บั๊กนี้อยู่ได้นาน
และเป็นเหตุผลที่ผมต้องใส่ log ชั่วคราวเพื่อหาต้นตอ **ใส่ `console.error` ไว้ถาวรแล้ว**
ถ้าไม่แก้จุดนี้ บั๊กหน้าตาเดียวกันจะซ่อนตัวได้อีก

### ขอบเขตความเสียหายที่ผ่านมา

บั๊กนี้อยู่บน production ด้วย เพราะ migration ตรงกัน แปลว่า
**ยังไม่เคยมีใครตั้งนัดผ่านหน้าเว็บได้สำเร็จเลย** นัดที่เห็นในระบบมาจาก seed ทั้งหมด
ซึ่งรันในสิทธิ์ `postgres`
